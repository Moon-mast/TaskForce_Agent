# 07-接口设计与移植方案

> 本篇回答两个问题:rag_0.1 作为独立包**如何对外暴露能力**(facade / contracts / cli / tests),以及**如何替换旧 `src/tools/rag/`** 而不炸主线。前者决定这个模块能不能整体拷走复用,后者决定它最终能不能落地。

## 一、模块目标与边界

- 定死对外接口面:包级 facade 暴露 `ingest` / `search` / `evaluate` 三个函数(**模块 06 落地后已补齐**),全部数据契约集中在 `contracts.py`。
- 论证可移植性的三条硬保证:零项目依赖、全同步、无 import 副作用。
- 给出旧系统(`src/tools/rag/`)的接口面对照、替换点清单与移植步骤 0~7 的路线(含风险与回滚)。
- 边界:本篇只定契约与路线,不写实现;**在切换完成前不改动旧系统任何文件**,旧路径全程保持可运行(回滚依托)。

## 二、设计决策与理由

### 2.1 三入口 facade,不暴露内部类

调用方(未来的 agent 侧、API 路由、CLI)只允许依赖三个函数签名与 `contracts.py` 里的 dataclass。内部模块(parse/clean/chunk/embed/store/retrieve)随各分篇自由重构,不构成对外承诺。

- 备选:像旧系统那样暴露 `RAGStore` 类面(`upload/search/delete/list_docs` 四方法,见 4.5 对照表)。不选——类面把存储实现细节泄漏成契约,旧系统里 `api/routers/knowledge.py:20/34/42` 与 `cli/commands/knowledge.py:17-41` 都是直接 `RAGStore()` 实例化,每处调用都耦死了"pgvector + 四方法"这个实现,替换时要动每一处。facade 收口后,替换只发生在一层薄适配里。
- 管理类操作(`按 doc_id 删除`、`列文档`)不走 facade 三入口,由 `store.py` 直接提供、`cli.py` 直调——它们是运维动作,不是检索能力,没必要进产品调用面。

### 2.2 contracts.py 集中全部数据契约

六个 dataclass(`ParsedDoc` / `ParentChunk` / `ChildChunk` / `RetrievedChunk` / `IngestReport` / `EvalReport`)只在 `contracts.py` 定义,其它模块一律 `from .contracts import ...`,与本项目"契约唯一出处"纪律(agent/contracts 的做法)同构——学过主图契约的写法,这里照搬经验。

### 2.3 可移植三条硬保证

1. **零项目依赖**:不 import `agent/`、`tools/`、`settings/` 任何包。包内一律**相对 import**(`from .contracts import ChildChunk`),这样目录整体拷到任何位置,包内引用零改动,只有包外调用方写一次绝对路径。
2. **配置自读**:只读 `RAG2_` 前缀环境变量(Milvus 地址、embedding 模式与 API key、VLM 开关等),不碰 `settings/config.py`。旧系统依赖 `settings.database_url` / `db.get_conn` / `ensure_vector_ext`(调研结论),这是它搬不走的原因之一。
3. **无 import 副作用**:`import rag_v01` 不得连 Milvus、不得加载 embedding 模型、不得创建目录。重活全部 lazy:store 连接与 embedder 都做成模块级 `lru_cache` 单例函数(`get_client()` / `get_embedder()`,见 04 篇 §4.1/§4.3),首次调用才初始化。这不仅为了移植,也是单测能 monkeypatch 的前提(4.4)。

### 2.4 全同步在新模块如何落地

pymilvus 的 `MilvusClient` 与 ragas 的 `evaluate()` 本身就是同步 API,全同步纪律在这里是"顺水推舟"而非约束——唯一要忍住的是 docling/句子模型文档里偶见的 async 示例一律不用。与主项目方案 A(线程池并行,ADR-0009)天然兼容,移植进 agent 时不需要任何 async 适配。

## 三、数据流与接口契约

### 3.1 facade 三入口

| 入口 | 签名 | 产出契约 | 上游分篇 |
|---|---|---|---|
| `ingest` | `ingest(paths: list[str \| Path]) -> IngestReport` | `IngestReport` | 编排 [02](./02-文档解析与噪声处理.md)→[03](./03-父子分块策略.md)→[04](./04-嵌入与Milvus索引.md) |
| `search` | `search(query: str, top_k: int \| None = None) -> list[RetrievedChunk]` | `list[RetrievedChunk]` | [05](./05-混合检索与RRF融合.md) |
| `evaluate` | `evaluate(testset_path: str \| None = None, report_dir: str = "./eval_reports", *, samples_path=None, system_label="rag_v01", limit=None) -> EvalReport` | `EvalReport` | [06](./06-ragas评估.md)(**需评估环境** `eval/`, 见 06 篇 §2.7) |

数据流总览(与 [00-总览](./00-总览.md) 一致):`ingest` = parse→clean→chunk→embed→store;`search` = 双路 top-20→手写 RRF(k=60)→top-5 子块→按 parent_id 回溯 parents 取父块并按父去重;`evaluate` = 检索 + 最简回答生成 + ragas 四指标。

**内存纪律(硬约束, 写 `ingest.py` 时不许破)**:`ParsedDoc` 只在内存里传递(02 篇不落盘, 见 02 篇 §三 接缝约定), 所以**必须逐文件处理**——`for path in paths: parse → clean → chunk → embed → upsert → 丢弃`, 峰值内存 = 最大单文件的解析产物 + 该文件的子块向量, 与语料总量无关。禁止"先把所有文件 parse 完再统一入库"(那是把整语料的 items + 向量攒在内存里, 语料一多就炸)。要留意的三处放大: ① 向量是 Python `list[float]`, 1024 维一组实测约 32 KB(list 槽 8 KB + float 对象 24 KB), 单文件级没问题、跨文件批处理才会失控(真要批处理就换 `array('f')`/numpy float32, 省 8 倍); ② 图片 base64 只在 04 篇每请求 ≤5 张的窗口里瞬时存在, 且 02 篇已把图片字节外置到磁盘只留路径; ③ 长期驻留进程(如 API 里跑 ingest)不许把结果塞进模块级全局——模块级只放 `lru_cache` 的 client/embedder 单例, 不放数据(§4.4)。

### 3.2 contracts.py 契约示例(节选,以落地为准)

```python
# 本篇只列 ingest() 与 facade 的报告契约; 其余四个契约的形状以各自分篇为唯一出处(见下方注)。
@dataclass
class IngestReport:
    ok_sources: list[str]            # 成功入库的文件名
    failed: dict[str, str]           # 文件名 -> 失败原因(解析失败/入库失败)
    total_parents: int
    total_children: int
    warnings: dict[str, list[str]]   # 文件名 -> 警告(解析 warnings / 清洗统计 / 超长前置检查等,02/04 篇)

@dataclass
class EvalReport:
    metrics: dict[str, float]        # context_precision/context_recall/faithfulness/answer_relevancy
    question_count: int
    report_dir: str                  # json+markdown 基线报告落盘位置
```

`ParsedDoc`(02 篇)、`ParentChunk` / `ChildChunk`(03 篇 §3.1 九字段表)、`RetrievedChunk` / `ChildHit`(05 篇 §3.2,父块上下文 + 命中子块明细)的字段以各自分篇为唯一出处,此处不重复定义。

### 3.3 元信息九字段(定稿,逐字)

`chunk_id, parent_id, doc_id, source, page_no, heading_path, chunk_type(text|table|image), char_len, created_at`——父块同样携带(其 `parent_id` 为空)。命名固定,不得增删改名;Milvus 侧落地为 children 的标量字段 + metadata(JSON),见 [04](./04-嵌入与Milvus索引.md)。

## 四、实现要点

### 4.1 __init__.py 骨架

**落地版(2026-09-21,以代码为准;与骨架的出入见 §4.7)**:

```python
"""rag_v01 —— 知识库 RAG 的包级 facade: 只暴露 ingest / search 两个入口(07 篇 §4.1)。"""
from __future__ import annotations
from pathlib import Path
from .contracts import ChildHit, EvalReport, IngestReport, RetrievedChunk   # 契约: 顶层 import 零代价

__all__ = ["ingest", "search", "evaluate", "ChildHit", "EvalReport",
           "IngestReport", "RetrievedChunk"]

def ingest(paths: list[str | Path]) -> IngestReport:
    """parse → clean → chunk → embed → store 的流水线编排(02/03/04 篇)。"""
    from .pipeline import run_ingest        # 流水线模块延迟 import: 否则 import rag_v01 会拉起 docling
    return run_ingest(paths)

def search(query: str, top_k: int | None = None) -> list[RetrievedChunk]:
    """双路 top-20 召回 + 手写 RRF(k=60)融合取 top_k, 再按 parent_id 回溯父块去重(05 篇)。"""
    from .retrieve import search as run_search   # 同上: 延迟 import, 不拉起 pymilvus
    return run_search(query, top_k)

def evaluate(testset_path=None, report_dir="eval_reports", *, samples_path=None,
             system_label="rag_v01", limit=None) -> EvalReport:
    """ragas 四指标评估(06 篇); 评估库只在独立评估环境里, 主环境调用会抛带跑法的 ImportError。"""
    from .evaluation import run_eval             # 注意模块名是 evaluation(见 §4.7 第 6 条)
    return run_eval(testset_path, report_dir, samples_path=samples_path,
                    system_label=system_label, limit=limit)
```

**落地时真踩到的坑(命名冲突, 见 §4.7 第 1 条)**: 流水线模块**不能**叫 `ingest.py` —— 它与 facade 的公开函数 `ingest` 同名, 一旦该子模块被 import, Python 会把父包上的 `ingest` 属性从函数**换成模块**(第一次调用正常, 之后 `rag_v01.ingest(...)` 报 `TypeError: 'module' object is not callable`)。所以模块名定为 `pipeline.py`。

坑位:`__init__.py` 里 import 的子模块若在 import 期做重活(如 `embed.py` 顶层加载 sentence-transformers),facade 的"无副作用"就破了——各子模块把初始化收进 `lru_cache` 单例函数,模块顶层只放 import 与常量。

### 4.2 cli.py 设计(风格对齐旧 src/tools/rag/cli.py)

子命令与参数:

| 子命令 | 参数 | 行为 |
|---|---|---|
| `ingest` | `<路径...>`(文件或目录) | 批量入库,打印 IngestReport 摘要(成功/失败/父子块计数) |
| `search` | `<query>` `[--top-k N]`(默认 5) | 打印每条 `[最佳命中的 rrf_score] source#chunk_id: 命中子块 text 前 80 字符`(取值见 05 篇 §3.2 的 `RetrievedChunk` / `ChildHit`; 对齐旧 cli 的展示格式) |
| `evaluate` | `[--testset 路径]` `[--report-dir 目录]` `[--limit N]` `[--samples 路径]` `[--label 名]` | 跑 ragas 四指标并落盘报告; `--limit` 试跑看账单, `--samples` 走「仅评估」入口, `--label` 给系统起名(**新旧对比靠它**: 旧系统用 `--label tools_rag_v1`, 报告里才会出现并排对比表); 需评估环境, 见 06 篇 §2.7 |
| `list` | 无 | 列文档(运维, 直调 `store.list_docs`) |
| `delete` | `<doc_id...>` | 按 doc_id 删文档(运维, 直调 `store.delete_doc`) |

沿用旧 cli 的三件套风格(见 `src/tools/rag/cli.py:14-26`,本次已读):手工 `sys.argv` 解析(不引 argparse 也行,子命令多后建议 argparse 但保持子命令名不变)、`USAGE` 字符串、出错 `raise SystemExit(1)`。另外补 `list`(列文档)与 `delete <doc_id>` 两个运维子命令,直调 `store.py`,不进 facade。

```python
import sys
sys.stdout.reconfigure(encoding="utf-8")   # 必须先于任何 print,见下方坑位
from .ingest import run_ingest

USAGE = "用法:python -m rag_v01.cli ingest <路径...> | search <query> [--top-k N] | list | delete <doc_id>"

def main() -> None:
    args = sys.argv[1:]
    if not args or args[0] not in ("ingest", "search", "list", "delete"):  # evaluate 随模块 06 加
        print(USAGE); raise SystemExit(1)
    # ... 分发到各子命令,风格同旧 cli.py 的 if/elif 链
```

**Windows 坑(实测过的旧账)**:Windows 控制台默认 GBK,直接 print 中文/表格 Markdown 会 `UnicodeEncodeError`,必须在入口模块最前 `sys.stdout.reconfigure(encoding="utf-8")`——旧 `src/tools/rag/cli.py:8` 就是这么干的,新 cli 照抄。注意两点:reconfigure 必须发生在**任何 print 之前**(import 顺序上放最顶);且只在 cli.py 这个入口模块做,**库模块(store/retrieve 等)不许动全局 stdout**——模块要可移植,不能带着全局副作用搬家。项目 ruff 对入口文件已有 per-file-ignore 配置。

### 4.3 移植锚点:兼容旧 kb_search 的 JSON 契约

旧 retriever 的唯一入口是 `kb_search` 工具(`kb_search.py:25`):返回 JSON 数组,每项键为 `doc_id/filename/seq/content/score`,content 截 500、top_k 钳 1-10;`retriever.py:30` 的 `_collect_hits` 解析该 JSON 并按 `(doc_id, seq)` 去重(以上来自调研结论)。移植时**适配层放 agent 侧**(如 `agent/subagents/` 下新写 `kb_search_v2` 工具,内部调 `rag_0.1.search`),不放进 rag_0.1——包保持零依赖。字段映射:

| 旧 JSON 键 | 新来源 | 说明 |
|---|---|---|
| `doc_id` | `RetrievedChunk.doc_id` | 直接映射 |
| `filename` | `RetrievedChunk.source` | 直接映射 |
| `seq` | 子块在文档内的序号,ingest 时写入子块 metadata(JSON) | 兼容 `(doc_id, seq)` 去重键;不进九字段(定稿不可增),只进 metadata |
| `content` | `parent_text + "\n---\n" + hits[0].text` 截 500 | 父块上下文进 content 是升级点 |
| `score` | `hits[0].rrf_score`(父块内最佳命中子块的 RRF 分) | 同为"越大越相关",方向一致**无需取反**;但 RRF 分数量级约 ≤ 2/(60+1)≈0.033,展示别用 `:.4f` 之外的科学计数 |

### 4.4 tests 策略:不依赖真实 Milvus / LLM

`src/rag_v01/tests/` 内单测,延续项目 fake/monkeypatch 模式:

- **FakeEmbedder**:实现 embed.py 的同形接口,输入文本→确定性 1024 维向量(如按字符 ordinal 播种生成),不加载任何模型。用它替换 `get_embedder()` 的 `lru_cache` 单例,ingest→search 全链路即可离线跑通。
- **假 Milvus**:pymilvus 只在 `store.py` 出现,且入口收敛到一个 `get_client()` 单例函数——单测 monkeypatch 它,换成内存版 FakeClient(dict 实现 insert/search/query/delete 接口子集)。这样 chunk 落库字段完整性、按 doc_id 删除等可测。
- **纯函数直测**:clean 规则(02)、父子切分边界与表格不切(03)、手写 RRF(k=60)排序与父块去重(05)都是纯函数,不碰任何假件,测试价值密度最高。
- **evaluate 的测法**:monkeypatch judge LLM 与最简回答生成为固定返回,只测 EvalReport 组装与 json+markdown 落盘,不测真实 ragas 打分。
- **边界(明确不测)**:真实 Milvus 的 HNSW/BM25 Function 行为(那是 [01](./01-环境与依赖.md)/[04](./04-嵌入与Milvus索引.md) 的实测待验证项)、embedding 质量、ragas 分数合理性——这些靠 06 篇的真机基线报告兜底。
- 注入点设计成 `lru_cache` 单例函数,与旧系统 `_default_store()`(`kb_search.py:19`)同构——调研结论点 4:保留同构注入点可少改测试。

### 4.5 旧系统接口面对照与替换点清单

旧系统现状(调研结论,2026-09 快照,**未运行验证**):`tools/rag/` 是已收口的 BM25(jieba)+pgvector+RRF 双路融合(TODO.md: 191 passed, 2026-09-14);当前工作区**正半途重命名 rag→rag_0.1**——测试 monkeypatch 字符串已改指 `tools.rag_0.1.kb_search`,但目录与 import 仍是 `tools.rag`。本次实读 `src/tools/rag/cli.py` 亦见此状态:docstring(`cli.py:1`)与 USAGE(`cli.py:15`)已写 `tools.rag_0.1.cli`,而 import(`cli.py:12`)仍是 `from tools.rag.store import RAGStore`。**移植第 0 步必须先把这个半途状态收干净,否则字符串 monkeypatch 点指空。**

旧接口面(签名@文件,均来自调研结论):

| 旧接口 | 位置 | 新系统对应 | 替换动作 |
|---|---|---|---|
| `parse_document(path)->str` | parse.py:10 | `parse.py` docling→`ParsedDoc` | 适配层不再用旧 parse |
| `split_text(text)->list[str]`(500/100 递归) | split.py:10 | `chunk.py` 父子分块 | 契约升级,重写 |
| `make_embeddings/embedding_dim/embed_texts` | embed.py:20/32/41 | `embed.py` 双模式(默认百炼多模态 `qwen3-vl-embedding`, DashScope SDK) | **保留旧 embed.py**——被长期记忆复用(见下) |
| `tokenize/Bm25Index/rrf_fuse` | bm25.py:32/45/86 | Milvus 内置 BM25 + 手写 RRF | 整文件下线 |
| `RAGStore().upload/search/delete/list_docs` | store.py:45/113/212/227/236 | `ingest()` / `search()` / `store.py` 的 delete/list | 需等价方法或适配层(见下) |
| `@tool kb_search`(JSON 契约) | kb_search.py:25 | 适配层 `kb_search_v2`(4.3) | retriever 唯一入口,必须兼容 |
| `cli.main()`(upload/list/delete/search) | cli.py:20 | 新 `cli.py`(ingest/search/evaluate) | 风格对齐,子命令更名 |

调用方清单(文件:行号,来自调研结论):`agent/subagents/retriever.py:22` import、`:94` `tools=[kb_search]` 装配、`:30` `_collect_hits` 解析;`api/routers/knowledge.py:20/34/42` 直调 RAGStore(每请求新建实例);`cli/commands/knowledge.py:17-41` 直调 RAGStore;`settings/db/store.py:14` **长期记忆复用 `embed_texts/embedding_dim`(跨模块耦合)**;tests 七处(test_rag/test_kb_search/test_graph/test_bm25/test_rag_hybrid/test_retriever/test_api)。

替换点清单(按依赖顺序):

1. **kb_search JSON 契约**(retriever 唯一入口,`(doc_id, seq)` 去重、content 截 500、top_k 钳 1-10)——适配层保契约(4.3)。
2. **RAGStore 四方法面**(API/CLI 双入口直调)——新系统给等价面:upload→`ingest`、search→`search`、delete/list→`store.py` 直供;API/CLI 路由各改一处调用。
3. **embed 被长期记忆复用,旧 `tools/rag/embed.py` 不可随旧 RAG 删除/改名**(调研结论点 3)——下线时单独保留或把长期记忆改指新 embed,二选一,见 4.6 步骤 6。
4. **测试注入点** `_default_store` 与 `kb.RAGStore` 两个 monkeypatch 锚——新系统 `lru_cache` 单例同构,测试改字符串路径即可,字符串须与最终包名一致(先收干净半途重命名)。
5. **score 语义**:融合分越大越相关(ROADMAP §7 登记契约),新 RRF 分同向,契约不变。

### 4.6.2 新旧双跑对比(2026-09-22, 40 题同集)

对照条件: 两侧**同一份语料**(DuReader-Robust 500 段, 旧侧入库 500/500 篇零失败, 新侧 499 篇 —— 有 2 篇同内容被内容寻址合并)、
**同一套 50 题里的 40 题**、**同一个最简生成器**(固定 prompt + `temperature=0`, 06 篇 §2.5)与**同一个 judge**(`deepseek-flash`)。
差别的只有检索内核与它原生的上下文口径(旧侧 = 500 字切片, 新侧 = 父块), 这正是要比的东西。
旧侧不跑本包的检索链路, 只由一次性脚本产出中间产物 jsonl 再走 `cli evaluate --samples`(脚本用完即删)。

| 指标 | 旧 `tools_rag_v1` | 新 `rag_v01`(基线) | 新(重跑) | Δ(新基线 − 旧) |
|---|---|---|---|---|
| context_precision | 0.6896 | **0.8958** | 0.8932 | **+0.2062** |
| context_recall | 0.9000 | **0.9500** | 0.9500 | +0.0500 |
| faithfulness | 0.8681 | **0.9595** | 0.9118 | +0.0914 |
| answer_relevancy | 0.4774 | **0.5015** | 0.4735 | +0.0241 |
| NaN 题数 | 9/40 | 7/40 | 10/40 | — |

**结论(带刹车)**: **四项全升, 但只有上下文精度这一项明确超出噪声带**。上一轮的复现性实测给出判读阈值 ——
输入固定时, judge 自身抖动是 faithfulness Δ0.20 / answer_relevancy Δ0.09, 检索侧 Δ≤0.003(06 篇坑位 12c);
再考虑新系统两轮之间的抖动, 拿两轮均值比的话 Δ 分别是 精度 +0.2049 / 召回 +0.0500 / 忠实度 +0.0676 / 相关度 +0.0101。
所以能下的结论是: **新内核在"喂给模型的上下文里有多少是相关的"这一项上有实质提升(约 +0.20), 而且它给的是父块全文而不是 500 字切片**;
其余三项方向为正但落在噪声带内, 不足以单独下结论 —— 这也与 06 篇"差异小于 ~0.1 不下结论"的口径一致。

**一处报告口径的已知瑕疵**: 报告 meta 里的"语料快照"(`doc_count/children`)是评估时从 **Milvus** 读的, 描述的是新内核的库;
旧系统那一侧的真实库是 pgvector(500 篇), 报告里看不出来。对比读数字时知道这点即可。


### 4.7 落地记录(2026-09-21)

1. **流水线模块叫 `pipeline.py`, 不叫 `ingest.py`**: 后者与 facade 的公开函数 `ingest` **同名**, 而 Python 在 import 子模块时会把父包上的同名属性换成模块对象 —— 于是"第一次 `rag_v01.ingest(...)` 能用、第二次 `TypeError: 'module' object is not callable`"。这种"用一次才炸"的坑最费时间, 直接换名消灭掉(单测里留了回归用例钉住); 公开 API 名仍按本篇定稿叫 `ingest`。
2. **facade 的子模块 import 放进函数体内**(骨架写的是顶层): `contracts` 留在顶层(纯 dataclass, 零代价, 且 `RetrievedChunk` 必须能 `from rag_v01 import`), 而 `pipeline` / `retrieve` 延迟 import —— 否则 `import rag_v01` 会连带拉起 docling 与 pymilvus, 违反 §2.3 的"无 import 副作用"。
3. **`search(query, top_k=None)` 而非 `top_k=5`**: 默认值只留 `config.py` 一处(与 05 篇 §4.6 同一口径)。
4. **`ingest` 加了"同源旧版本清理"**(`store.purge_stale`): doc_id 是文件内容 hash, 文件改过重灌会在库里留下新旧两份、检索同时命中。现在 `pipeline._ingest_one` 在写入前按 `source` 清掉其他版本的 doc_id, 并把这件事写进该文件的警告。这一步不在本篇原设计里, 是落地时补的运维正确性。
5. **子模块名不得与 facade 的公开函数同名**: 流水线模块因此叫 `pipeline.py`(不叫 `ingest.py`), 评估模块叫 `evaluation.py`(不叫 `evaluate.py`) —— 否则 import 子模块会把父包上的同名属性**换成模块对象**, 「先用正常、之后 `rag_v01.evaluate(...)` 就变成调用模块」; 单测留了回归用例(import 子模块后再断言 facade 的入口仍是函数);
6. **CLI 的子模块 import 全部按子命令懒加载**(每个 `_cmd_*` 里各自 import): 跑 `evaluate` 不该把 docling(连带 torch)拉起来 —— 评估环境里没有可用的 torch, 顶层 import 会让 `evaluate` 子命令直接起不来; 单测的 patch 点相应改到源模块(`rag_v01.pipeline.run_ingest` 等);
7. **CLI 入口命令是 `python -m rag_v01.cli`**(骨架写的是 `python -m new_module.rag_0.1.cli`, 那是包改名前的旧路径), 子命令落地为 `ingest` / `search` / `list` / `delete` / `evaluate`(模块 06 落地后补齐); `search` 的输出在 `[rrf_score] source#chunk_id` 基础上补了**两路名次** `d1/s2` —— 05 篇 §五的验收明确要求这三列可见。
