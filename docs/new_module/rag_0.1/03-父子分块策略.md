# 03-父子分块策略

> 对应代码: `src/rag_v01/chunk/`(包: `__init__.py` 只管编排 / `common.py` 共享小件 / `parents.py` 父块侧 / `children.py` 子块侧) | 数据契约: `contracts.py` 的 `ParentChunk` / `ChildChunk`
> 上游: [./02-文档解析与噪声处理.md](./02-文档解析与噪声处理.md) 产出的 `ParsedDoc`; 下游: [./04-嵌入与Milvus索引.md](./04-嵌入与Milvus索引.md) 的 embed / store。

## 一、模块目标与边界

切块是 RAG 流水线里少数的"纯函数"环节: 输入确定则输出确定, 不碰网络、不碰数据库。本模块做两件事:

1. **父块切分(结构感知)**: 沿 docling 结构树的标题层级边界聚合内容单元, 产出目标 1200~1800 字符的"大而全"父块;
2. **子块切分(递归字符切分)**: 在每个父块内部, 按 段落 -> 换行 -> 中文句号等 的分隔符层级递归切出目标约 450 字符、相邻重叠约 50 字符的"小而准"子块。

边界(不做什么):

- 不做嵌入与向量化(04 篇)、不做存储与索引(04 篇)、不做检索与融合(05 篇);
- 不重新解析文档——标题层级、页码、表格 Markdown、图片落盘路径均由 02 篇解析阶段挂好, 本篇只消费;
- 零第三方依赖、零 IO, 纯标准库——本篇因此是全模块最易单测的一环(tests/ 无需任何 fake)。

## 二、设计决策与理由

### 2.1 为什么是父子分块(small-to-big)

检索质量里藏着一对天然矛盾:

- **匹配端要小块**: 向量嵌入对小而聚焦的文本更锐利——长文多主题互相平均, 向量"糊"; BM25 的词频信号同样在小块上区分度更高, 块越大词项被稀释得越厉害;
- **生成端要大块**: 送进 LLM 的上下文必须完整——命中的那半句话往往依赖前后文才有意义, 只给 450 字符经常出现"答案的另一半在隔壁块"。

单层切分只能两头凑合: 切小了检索准但上下文残缺, 切大了上下文全但检索糊。父子分块把两个诉求拆开: **子块进索引承担匹配, 父块进生成承担上下文**, 命中子块后按 parent_id 回溯父块(05 篇链路)。代价是多一级 parents collection 存储与一次主键回查——在 Milvus 里按主键查父块, 代价可忽略。

| 策略 | 匹配精度 | 上下文完整性 | 边界语义破坏 | 存储 | 复杂度 |
|---|---|---|---|---|---|
| 固定窗口(如 512 字符硬切) | 中(窗口内主题混杂) | 差(句子拦腰截断) | 频繁 | 1 份 | 最低 |
| 纯递归字符切分(单层) | 中高(边界对齐) | 中(块小则残、块大则糊, 只能选一头) | 少量 | 1 份 | 低 |
| 整篇不切 | 差(向量平均化, BM25 文档级稀释) | 好 | 无 | 0.5 份 | 最低 |
| **父子分块(本项目)** | **高(子块 ~450 字符小而准)** | **好(父块 1200~1800 大而全)** | 双层保护(父沿标题、子沿句子) | ~1.3 份(含重叠) | 中(两级 ID 映射 + 回溯) |

说明: 纯递归字符切分不是被否决, 而是被**降级使用**——它仍是子块层的算法; 被否决的是"只递归切一层"的方案。整篇不切在本项目语料(技术文档、含表格)下不可行, 列入对比仅为完整性。

### 2.2 父块切分: 沿标题层级边界聚合

规则按优先级:

- **边界规则**: 遇到与当前标题栈顶**同级或更浅**的标题 → 闭合当前父块。父块绝不跨节, 保证一个父块的 heading_path 单义;
- **上限规则**: 累计字符将超 1800 → 在当前内容单元前闭合旧块、新块从该单元起算;
- **下限不强制**: 短节就是短父块, 不为凑 1200 跨标题边界("宁小勿跨节")。1200~1800 是目标带不是硬约束, 验收看达标率(§五), 不追求 100%;
- **超长无标题段落退化**: 导言、法律条文这类数千字符无标题的正文, 单元自身超长时, 对该单元退化为递归字符切分补出边界(复用子块切分器, 目标改为 1800), 产物各自成父块;
- **表格整块不切**: 表格是原子内容——Markdown 序列化的表格从中间切开即毁掉行列结构, 宁可整表超长。超长表格的检索质量由子块层兜底: 整表即一个子块(§2.3), BM25 对表内词项的精确匹配仍然有效, dense 侧变糊可接受;
- **标题进正文**(实现补定): 标题单元不是只入标题栈, 它同时进父块正文。BM25 只索引 `text` 字段, 标题词往往是该节最强的检索信号, 不写进正文就永远匹配不上; 子块也因此自带语义锚点;
- **不留"只有标题"的父块**(实现补定): 标题后面紧跟着原子块或超长正文时, 收口会先产出一个只装标题的块 —— 它的子块就是标题本身, 命中它等于没有上下文。这种块统一并进紧随其后的那一块(标题当锚点), 见 §4.6 坑位四。例外: 后面那块自己以标题开头(空章节接下一节)则不并, 否则新节内容会顶着上一节的面包屑。

> 待验证: 表格父块若长达数千字符, dense 嵌入明显变糊。若语料出现 > 4000 字符的巨表, 备选是按行组切表(每 N 行 + 重复表头)——首版不做, 实际语料出现再加。

### 2.3 子块切分: 递归字符切分 + 相邻重叠

分隔符层级从粗到细: `"\n\n"(段落) -> "\n"(换行) -> "。/！/？/；"(中文句号等) -> 硬切兜底`。

- **为什么是这个层级**: 段落是语义最完整的自然单元, 先按段落并/切; 段落仍超长降换行(列表项粒度); 再降中文句号(句子粒度); 全都切不动(无标点长串)才硬切。中文句号是最可靠的句界(坑位 2), 分号次之; 逗号太碎, 不入默认层级。
- **目标约 450 字符**: 与中短文本检索的典型粒度匹配——embedding 对 ~450 字符的局部主题表征充分, 能容纳 2~4 个完整中文句子形成局部主题, 又不至多主题混杂; 父子比约 1:3~1:4, 一次父块回溯的上下文信息量合适。
- **相邻重叠约 50 字符**: 约一个句子的尾巴, 防止关键信息恰落边界、两边都不完整。实现上, 重叠在子块序列合并完成后统一加: 取上一块尾部 ~50 字符、**回退到句子边界对齐**后拼到下一块头, 不做裸字符回退。
- **表格类父块不切子块**: 整表即一个子块, chunk_type=table, parent_id 指向该表格父块。图片同理(§三)。

**实现定稿(2026-09-21): 递归降级切分用库, 相邻重叠自己写。** 递归那一层交给 LangChain 的 `RecursiveCharacterTextSplitter`(分隔符层级、相邻小片合并、无标点硬切、每片起始偏移都由它负责, 位置见 §4.2/§4.7); **重叠仍由本模块自己加** —— 库的重叠按"整片"(句/段)量化, 窗口给 50 实测落 32~41、给 70 直接跳到 ~76(超出上限 60), 落点由语料句长决定, 做不到"取尾部 ≤50 字符、回退到句界、落在 40~50"。手写那版(约 90 行递归 + 合并 + 硬切)已被替换, 代价是**子块侧不再零依赖**(父块侧仍旧零依赖), 库的三个坑与"没有 slack 容差"这条行为变化记在 §4.7。

### 2.4 ID 与父子关联

| ID | 生成规则 | 说明 |
|---|---|---|
| doc_id | 文件字节流 SHA-256 的前 16 位 hex, 解析阶段算好挂在 `ParsedDoc` 上, 本篇透传 | 内容寻址: 同内容不同路径 → 同 doc_id(幂等); 内容变 → doc_id 变, 便于按 doc_id 删旧重灌 |
| parent_id | `f"{doc_id}:p{父块序号:03d}"` | parents collection 的主键 |
| chunk_id | 父块: 与 parent_id 同值; 子块: `f"{parent_id}:c{子块序号:03d}"` | children collection 的主键; 父块记录自身的 parent_id 字段为空 |

父子映射采用**扁平两列表 + parent_id 外键**式, 不做嵌套结构——与 Milvus parents/children 两个 collection 一一对应, 也免去 dataclass 互相嵌套的序列化麻烦。子块回溯父块 = `children.parent_id → parents` 主键查询(05 篇)。

确定性要求: ID 只由内容与序号决定, 不掺时间、不掺随机——同一文件切两遍, 除 created_at 外逐字段一致(§五验收)。

## 三、数据流与接口契约

```text
ParsedDoc (02 篇产出, contracts.py 定义)
   │  携带: doc_id, source, 内容单元序列(text/table/image/heading 四类,
   │        各含标题栈快照、page_no、表格 Markdown、图片落盘路径)
   ▼
chunk.split(parsed_doc) ──► (list[ParentChunk], list[ChildChunk])
   │                            │
   ├─ 04 篇 embed: 子块文本 → 1024 维 dense 向量
   └─ 04 篇 store: 写入 children / parents 两个 collection
```

- 输入: `ParsedDoc`(字段细节以 [./02-文档解析与噪声处理.md](./02-文档解析与噪声处理.md) 与 contracts.py 为准);
- 输出: 元组 `(parents, children)`, 两者均携带 §3.1 的九字段元信息; 父块的 parent_id 为空;
- 依赖 contracts.py 类型: `ParsedDoc`(读), `ParentChunk` / `ChildChunk`(写), 归属见 [./07-接口设计与移植方案.md](./07-接口设计与移植方案.md);
- 图片单元: 与表格同策略——作为一个原子单元参与父块聚合, 子块层整体产出一个 chunk_type=image 的子块, 其 text 为占位描述(默认)或 VLM 生成的描述(02 篇开关开启时), 图片路径入 metadata。

### 3.1 元信息字段表(九字段, 命名与全局定稿一致, 不得增删改名)

| 字段 | 类型 | 来源 | 用途 |
|---|---|---|---|
| chunk_id | str | 切块时生成: 父块 `f"{doc_id}:p{i:03d}"`(与 parent_id 同值), 子块再追加 `:c{j:03d}` | children collection 主键; 检索结果的唯一定位 |
| parent_id | str | 父块闭合时定; 父块自身为空串 | 命中子块后回溯父块(parents 主键); 父子映射的唯一纽带 |
| doc_id | str | 文件内容 SHA-256 前 16 位 hex(解析阶段生成) | 同文档聚合; 按 doc_id 整体删除重灌(store 的删除入口) |
| source | str | 文件路径(相对语料根, POSIX 风格) | 溯源展示: 告诉用户"依据来自哪个文件" |
| page_no | int \| None | docling 内容单元的 page provenance | 精确定位; md/docx 通常无页码记 None(pdf 才有, 以 02 篇实测为准) |
| heading_path | str | 解析期标题栈快照, 各级以 `" > "` 连接 | 语义面包屑: 命中结果展示 + 人工排查切块质量 |
| chunk_type | str | 单元类型: text / table / image | 检索过滤与结果渲染(表格按 Markdown 表喂 LLM) |
| char_len | int | len(text), 子块含重叠文本 | 切块质量统计: 父块 1200~1800 达标率、子块 ~450 的核心验收指标 |
| created_at | str | 入块时刻, UTC ISO 8601 | 排查与增量参考; 不参与 ID 生成, 不破坏确定性 |

三条补充(实现期定稿, 不定这里的字面规则就写不出对的代码):

1. **`char_len` 由 `text` 派生**: 它是 `Chunk` 的字段(不要手填), 由 `__post_init__` 按 `len(self.text)` 回填(重叠拼接、去空白后忘了同步是这类字段的经典 bug); `asdict()` 里照样有它, 04 篇落 metadata 不受影响。
2. **父块 `heading_path` 取"开块单元"的位置**: 开块是标题 → 标题自身也接上(`文档 > 第一章 > 1.1`), 开块是正文(规则 B 切出的续块)→ 直接用它的面包屑。父块不跨节保证这份面包屑单义。
3. **`image_path` 是透传字段, 不算十字段里的第十个**: 02 篇要求图片路径随元信息进 04 篇的 `metadata(JSON)`(多模态嵌入要按它读图), 所以 `ParentChunk` / `ChildChunk` 各多一个 `image_path: str | None`, 九字段命名与语义一个没动。

### 3.2 对外接口(落地版)

| 接口 | 签名 | 说明 |
|---|---|---|
| `split` | `(doc: ParsedDoc, cfg: Config \| None = None, *, clock: Callable[[], str] = _utc_now) -> tuple[list[ParentChunk], list[ChildChunk]]` | 唯一入口; `clock` 只为单测注入固定时间(created_at 是本模块唯一的非确定字段) |

`cfg` 只用到三个值: `parent_target_chars`(上限 = 目标 × 1.2, 退化阈值同此)、`child_target_chars`(直接当库的 `chunk_size`)、`child_overlap_chars`(重叠窗口)。

## 四、实现要点(API + 骨架 + 坑位)

### 4.1 骨架一: 父块聚合器(纯标准库)

```python
# chunk.py —— 父块聚合(骨架, 说明性质; 完整规则见 §2.2)
PARENT_MIN, PARENT_MAX = 1200, 1800

def split_parents(doc: ParsedDoc) -> list[ParentChunk]:
    parents, buf, size, stack = [], [], 0, []           # stack: 标题栈 [(level, title)]
    for unit in doc.units:                              # 02 篇的内容单元序列
        if unit.kind == "heading":
            if buf and unit.level <= stack[-1].level:   # 规则A: 同级/更浅标题 → 闭合
                parents.append(close(buf, doc, stack)); buf, size = [], 0
            push(stack, unit)                           # 更深 push / 同级换 / 更浅弹到父再 push
        elif size + unit.char_len > PARENT_MAX:          # 规则B: 将超上限 → 先闭合再装
            parents.append(close(buf, doc, stack)); buf, size = [unit], unit.char_len
        else:
            buf.append(unit); size += unit.char_len
    if buf:
        parents.append(close(buf, doc, stack))          # 规则C: 收尾不丢尾块(宁小勿丢)
    return parents                                      # table/image 单元同路径进入, 原子不拆
```

`close()` 内两处收尾: (a) 生成 parent_id(§2.4 规则)并快照 heading_path; (b) buf 中若有自身超长的无标题文本单元, 先对该单元做目标 1800 的递归退化切分再分别成块(§2.2)。

**落地版(2026-09-21, `chunk.py` 与上面骨架的三处差异)**:

| 骨架 | 落地 | 为什么改 |
|---|---|---|
| `unit.kind == "heading"` / `unit.char_len` | `item.is_heading` / `len(item.text)` | 契约定稿后只有 `ParsedItem`(02 篇 §三), 骨架那套字段名是方案期的写法 |
| 单元序列 `doc.units` | `doc.items` | 同上 |
| 靠 `close(buf, doc, stack)` 传栈快照 | 单元自带 `heading_path`(解析期快照), 父块取**开块单元**的位置, 开块是标题时把标题自身也接上 | 不必在切块层重建标题栈; 父块不跨节由规则 A 保证, 所以这份面包屑单义 |
| 无 | 标题**不进切分输入**, 只作前缀贴回第一片 | 标题与正文混着切时, 切分器"按片贪心、不回头"的合并会把标题单独关成几字符的碎块(实测出现 8 字符父块) |
| 无 | 子块切分改为**库调用**, 重叠自己加(§2.3 定稿, §4.7 三个坑) | 库的重叠按整片量化, 落点由语料句长决定, 做不到 40~50 的口径 |
| 无 | `absorb_heading_only` 收尾后处理(§4.6) | 骨架没覆盖"标题后紧跟原子块/超长正文"的中间态 |

### 4.3 坑位一: 重叠导致的 BM25 重复计分

- **机理**: BM25 是词频型打分。~50 字符重叠让相邻子块共享 1~2 句; 查询词若恰落在重叠区, 兄弟子块在 sparse 路同时靠前, RRF(k=60)按名次求和会互相抬分, top-5 子块名额可能被同一父块的 2~3 个兄弟占去——按父去重后有效父块不足 5 个, 上下文多样性受损。dense 路影响小(相邻块向量本就相近, 嵌入平滑)。
- **缓解**: (a) 重叠对齐句子边界且 50 字符封顶, 不贪多; (b) 05 篇父块去重后若有效父块 < top-5, 从融合排名向后补位; (c) 用 ragas 的 context_precision(06 篇)观测命中冗余。
- **定性**: 这是 small-to-big 配词频检索的固有摩擦, 是取舍不是 bug; 若观测严重, 把 OVERLAP 降到 30 再测, 权衡边界截断损失。

### 4.4 坑位二: 中文句子边界识别

- **引号**: `他说。"` ——闭引号应与前句同块。lookbehind 切分 `(?<=[。！？])` 会把闭引号甩给下一块头, 边界集需扩成 `(?<=[。！？]["』」]])` 一类;
- **省略号与连用**: `……`、`？！` 连用按单字符边界集天然覆盖, `…` 单独入集即可;
- **英文句点不入边界集**: 小数 `3.14`、缩写 `e.g.` 会误切。代价是中英混排文档里的英文长句一路降级到硬切层——可接受; 语料若转以英文为主, 换分隔符集即可(本项目以中文语料为主, 不预做);
- **验证办法**: 单测放"含引号对话 / 小数 / 省略号"的样例串, 断言切分点不落在这些符号内部。

### 4.5 坑位三: heading_path 面包屑构建

- **构建**: 解析期维护标题栈, 每个内容单元入列时快照当时栈, 用 `" > "` 连接各级标题(本篇局部约定, 全模块沿用)。栈操作: 更深 push、同级替换栈顶、更浅弹出至父级再 push;
- **层级跳号**(h1 直接跟 h3): 栈按 level 数值比较而非 +1 递进, 天然兼容;
- **pdf 误判**: pdf 的 heading 是 docling 预测结果, 加粗行可能被当标题, 面包屑带噪声。heading_path 只用于展示与排查, 不参与打分, 容忍; 误判严重时在 02 篇解析层加规则(如过滤过短标题), 不在本篇修;
- **同名标题**: 不同位置的同名标题会产生相同面包屑, 靠 doc_id + 序号区分, 不要求面包屑唯一。

### 4.6 坑位四: "只有标题"的空壳父块(实测发现)

- **现象**: 长文档冒烟里出现 `char_len=6` / `char_len=8` 的父块, 正文就是一行标题; 它的子块也是这一行标题, 检索命中它等于没有上下文, 纯噪声。
- **成因**: 两条收口路径都会先把标题单独关起来 —— (a) 标题后面紧跟**原子块**(表格/图片), 原子块必须独占父块; (b) 标题后面紧跟**超长正文**(单条 > 上限), 规则 B 要求"先闭合再装"。两种情况下缓冲里只有标题。
- **解法**: 收口后做一遍后处理, 把"只有标题"的块并进紧随其后的那一块(`_absorb_heading_only`), 标题成为下一块的语义锚点; 它对子块的价值也更大(子块文本里带上节标题)。
- **两条边界**: 后面那块自己以标题开头则不并(空章节接下一节, 并了会让新节内容顶着上一节的面包屑 —— 面包屑按开块单元取); 走到文档末尾还攒着则自己成块(全文只有标题的文档, 这就是全部内容, 宁小勿丢)。
- **验证**: `tests/test_chunk.py` 的 `test_heading_carries_into_atomic_block` / `test_heading_joins_oversized_body` / `test_empty_section_does_not_steal_next_heading`; 长文冒烟里的空壳标题块消失(改造前 3 个, 改造后 0 个)。

### 4.7 坑位五: 用库切分的四个坑(全部实测)

1. **`separators` 末尾必须带空串 `""`** —— 库靠它做"逐字符切 + 合并"的兜底。不写的话, 遇到完全无标点的长串(`'x' * 300`)库**整段不切**: 实测目标 100 时给出 1 片 300 字符, 直接超上限三倍。
2. **`keep_separator=True` 会把匹配到的分隔符贴到下一片开头**(实测下一片是 `'。他喊道:“就这样办'`), 不搬回则子块以标点开头。搬回时**闭引号也要一起搬**: 库只前移匹配到的 `。`, `”` 留在原地会产出 `'”然后转身离开房间…'` 这种片, 所以回搬字符集是 `。！？；…\n」』”）)]】"`。
3. **重载"文本 + 起点"的返回形状**: 库切出来的文本已去过首尾空白、分隔符也搬过位置, 用区间回切原文对不上 —— 所以接口从"区间"改成"(片段文本, 在正文里的起点)", 起点只用于回查页码。搬走的前导字符要把起点一起修正(`start += len(lead)`)。
4. **库严格封顶, 没有手写版那个 `slack` 容差**: 手写版允许片长落在 `[target, target + slack]`(一个 460 字符的段落能整段留着), 库则严格 `≤ chunk_size`(实测目标 450 → 最长 448; 逐字符兜底时正好 100/118)。**行为变化**: 比目标略长的段落会被降级切开。不影响验收线(450 目标 + 50 重叠 = 最长 500 ≤ 550), 但排查"为什么这块比预期碎"时要想到它。另外库偶尔吐末尾空片, 已在 `split_pieces` 里过滤。

> 教训记一条: 这三条都不是文档写着的, 全靠在隔离脚本里跑真实语料才现形 —— 换掉一个轮子时, 先拿"极端输入"(无标点长串、含引号对话、刚好超目标的段落)各跑一遍, 再动手改主流程。
