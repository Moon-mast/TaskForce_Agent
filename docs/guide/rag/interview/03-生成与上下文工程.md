# 03-生成与上下文工程(面试拷打)

> 一句话: 这一篇拷"检索到的材料怎么变成回答" —— 上下文怎么组织、预算怎么控、子智能体与主智能体怎么交接、以及哪些环节容易让模型跑偏。
> 用法: 先自己答, 再对照"答题骨架"; 深挖追问答不上来就回 [讲解 04 篇](../rag_v01/04-生成侧全链路.md)。

## Q1. 检索回来 5 个父块(每个一两千字), 你怎么交给模型?(基础)

**答题骨架**
不能原样塞进去 —— 5 × 1500 字就是 7500 字, 会挤掉对话历史、背景和其他子任务的结果。我的做法是分三层预算: 最多取 **4 条**依据、单条正文截 **250 字**、全部依据合计不超过 **1200 字**, 另外来源列表最多 5 条。检索结果先由检索子智能体压成**结构化结果摘要**(结论 + 要点 + 命中明细), 再由 answer 节点按这个预算把原文片段渲染进消息流。三层依次收紧, 保证总预算永远不破。

**深挖追问**
- "为什么不直接把 top-5 全文塞进去?" → 成本和上下文污染; 而且多子任务并行时, 每个子结果都要占额度。
- "1200 字会不会太少?" → 这是我做的取舍: 单条 250 字足够支撑一句话回答; 需要更多上下文时, 应该靠**切分与父子分块**把相关材料聚到同一个父块里, 而不是靠多塞。
- "依据进的是系统提示词还是消息流?" → 消息流(HumanMessage), 系统提示词只放静态内容 —— 为的是前缀缓存, 静态前缀重复命中, 每轮都变的依据不该污染它。

**证据锚点**: `agent/answer.py:26-29`(`EVIDENCE_ITEMS_MAX=4` / `EVIDENCE_ITEM_CHARS=250` / `EVIDENCE_TOTAL_CHARS=1200` / `SOURCES_MAX=5`)/ `_render_evidence`(37-76)/ `answer_node`(121-139)。

**常见错误答法**: 说"把检索结果拼进 prompt"。这个项目里"拼"是有明确预算与渲染格式的, 说不清预算就是没做过上下文工程。

## Q2. 为什么不直接把子块给模型? 子块不是更精确吗?(基础)

**答题骨架**
子块是**用来定位的**, 不是用来回答的。450 字的子块命中率高, 因为它聚焦; 但它很可能只含答案的一半语句 —— 答案往往跨越子块边界。所以我把命中子块**回溯到父块**, 用父块全文(1200~1800 字)作为上下文主体。这也让评估口径统一: 评估时的 `contexts` 用的就是父块文本, 和线上喂给模型的载荷同源。

**深挖追问**
- "那子块起什么作用?" → 它决定"哪个父块被选中"以及"在父块里哪一段最相关"(命中明细里的最佳子块文本会附在 content 后面, 用分隔线隔开)。
- "父块太小怎么办?" → 用真实文档量过: 短节文档必然产出小父块, 这是文档形态的函数, 不是 bug。真需要更大上下文时可以调 `parent_target_chars`, 但要重灌。
- "为什么评估也用父块?" → 如果评估用子块、线上用父块, 指标就不代表线上实际看到的材料。

**证据锚点**: `retrieve.py:155-171`(`_retrieved` 用 `parent_text`)/ `contracts.py:111-128` / `evaluation.py:173-174`(contexts 取父块且保持名次顺序)。

**常见错误答法**: 说"子块和父块都塞进去" —— 父子内容是重叠的, 重复塞是纯浪费预算。

## Q3. 子智能体为什么不只做检索, 还要是个 ReAct 循环?(进阶)

**答题骨架**
因为"用户的一句话"和"库里能查到的措辞"常常不一致。ReAct 循环让模型**用工具返回的内容决定下一步**: 第一轮发现某条 query 没命中相关材料, 它可以换措辞或拆出子问题再查一次。这相当于把"查询改写"这件事交给模型在循环里涌现, 而不是提前写一个改写模块。不过我给它的纪律比代码上限更严: 提示词里要求"首轮命中相关就收尾", 全程最多两次检索; 代码里 `MAX_ITERATIONS=5`, 是防失控的兜底。

**深挖追问**
- "为什么提示词和代码的上限不一样?" → 提示词管方向(别乱搜), 代码管失控(真搜起来有硬上限)。两层职责不同。
- "怎么防止它一直搜?" → 双层: 子图自数轮数 + 上下文 16k 字符预算闸门(超了注入收尾提示), 主图还有 `recursion_limit` 兜底。
- "搜完之后怎么得出结论?" → **不再调用额外 LLM**: 模型最后一条消息里的自然文本就是结论, 我用解析器抽结论与要点; 同时确定性地从所有工具消息里重建命中明细。

**证据锚点**: `agent/subagents/retriever.py:24`(`MAX_ITERATIONS=5`)/ `agent/subagents/react.py:30`(`CONTEXT_BUDGET_CHARS=16000`)/ `prompts/subagents/retriever.md` 的检索纪律 / `extract_answer`(react.py:58-77)。

**常见错误答法**: 说"我做了 query 改写模块" —— 这个项目是**让模型在工具循环里自己改写**, 不是独立模块, 说错会显得没读自己代码。

## Q4. finalize 为什么不调一次 LLM 把结果整理成结构化?(深水)

**答题骨架**
一开始就是这么设计的 —— 用 `with_structured_output` 把模型输出转成结构化摘要。实测发现问题: 对 QA 型任务, 模型倾向**直接在正文里回答**(因为它被要求"给出结论"), 于是结构化解析普通文本会崩。所以改成**不再发起第二次调用**: 结论从模型最后一条消息里解析(带 JSON 围栏就解析 JSON, 否则截断纯文本), 命中明细则由工具消息**确定性重建**。好处是零额外延迟、零额外成本、结果稳定可复现。

**深挖追问**
- "解析失败怎么办?" → 退化成"折叠空白后截前 100 字", 不抛异常; 结论上限 100 字是契约里的硬约束。
- "怎么判断模型被轮数掐断了?" → 看最后一条消息**是否还带 `tool_calls`**: 带着说明它还想调工具但被上限截停, 这时诚实返回 `partial` + warning, 而不是假装成功。
- "无命中为什么也不调 LLM?" → 直接返回"知识库未检索到相关内容"。让模型在没材料时自由发挥, 是最危险的一类失败。

**证据锚点**: `retriever.py:54-90`(三种收尾分支)/ `:29-47`(`_collect_hits` 确定性重建)/ `react.py:58-77`(解析与回退)。

**常见错误答法**: 说"用 LLM 做后处理更灵活"。这里是**实测过不可行**才换掉的, 讲出原因比讲设计更值钱。

## Q5. 子智能体的结果怎么回到主智能体?(进阶)

**答题骨架**
只能通过**一个结构化摘要**回传, 不能把子图里的上下文倒出去。检索子智能体回的是 `ResultSummary`: 状态(success/partial/need_clarification/failed)、不超过 100 字的结论、要点、`data.hits`(命中的结构化明细, 这是正文进入最终回答的唯一通道)以及 `sources`(去重后前 10 个文档 id)。主图的 supervisor 回收时把摘要渲染成一条消息追加进对话; answer 节点再按预算从 `data.hits` 里取原文。

**深挖追问**
- "为什么不用共享上下文?" → 子图有自己的私有消息键(`react_msgs`), **不能**叫 `messages` —— 共享键直挂模式下, 同名键会让子图的工具消息并进主图历史, 主图上下文立刻被检索原文污染。这是这个项目的一条架构红线。
- "路由时看不到正文会不会决策不准?" → 路由只看决策字段(状态、结论)是有意的, 正文留给 answer; 两处渲染用不同的证据开关。
- "结果摘要的字段有什么硬约束?" → 结论 ≤100 字**保留**校验(决策字段), 任务描述不加长度上限(它是模型自由生成的文本, 加会崩整轮)。
- "并行多个子任务呢?" → 结果列表由 reducer 累加; 异步派发回收时**必须写回 state**, 否则 answer 读到空。

**证据锚点**: `agent/contracts/summary.py:18-38` / `retriever.py:80-89`(`data={"hits": hits}`, `sources`)/ `react.py:39`(私有键红线)/ `supervisor.py:82-105`。

**常见错误答法**: 说"子智能体和主智能体共享 messages"。这是被 ADR 明确否掉的做法。

## Q6. 用户反馈"答错了", 你怎么判断是检索问题还是生成问题?(实战)

**答题骨架**
先看**材料对不对**, 再看**模型有没有用好材料**。我的评估报告里每道题都有"参考答案 / 生成回答 / 上下文数 / 四个分数", 还有 `debug` 字段记录命中的两路名次 —— 所以能直接区分三种情况: ① 相关材料没进 top-5 → 检索问题(看是 dense 还是 sparse 没召回, 或者分块把答案切碎了); ② 相关材料进了但回答里没有 → 生成问题(上下文预算把它截掉了, 或者提示词纪律没生效); ③ 材料相关、回答也对但不够切题 → 相关度问题(那通常与答案太短/太笼统有关, 不是检索的错)。线上排障的快速办法是 `cli search` 直接复现这一刻的检索结果。

**深挖追问**
- "怎么发现是预算截断了?" → 依据条数上限是 4、总量 1200 字, 如果相关块排在第 5 位, 它压根没进模型 —— 看 `rrf_rank` 就能确认。
- "生成问题怎么改?" → 先看提示词纪律(是否要求只依据材料、是否要求冲突明示), 再考虑是否该把上下文组织方式改掉。
- "有没有自动化?" → 目前靠评估报告的逐题表 + `debug` 名次, 没有做自动归因工具。

**证据锚点**: [讲解 04 篇](../rag_v01/04-生成侧全链路.md) §六 / [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.1 的四指标→环节映射 / `evaluation.debug_of`(122-139)。

**常见错误答法**: 一上来调温度、换模型。**先分清检索与生成**, 否则你在错误的环节上花钱。

## Q7. 提示词里为什么要写"只依据材料回答, 资料不足就说不知道"?(基础)

**答题骨架**
因为 RAG 最坏的一类失败不是"答不出来", 而是**没查到却编一个像样的答案** —— 用户无法分辨, 信任成本很高。所以我把纪律写死在提示词里: 只依据命中内容、禁用外部知识、材料不足就直说"根据资料无法回答"。代价是问不到就会得到一句兜底话术, 这也是我评估里 `answer_relevancy` 偏低的一个原因(兜底话术忠实但相关度为 0) —— 这个取舍我认。

**深挖追问**
- "怎么量化这个取舍?" → 评估里能直接看到: 兜底话术的 faithfulness 是 1.0 但 answer_relevancy 是 0.0; 所以相关度指标低有一部分是**有意的保守**造成的。
- "除了禁用外部知识还写了什么?" → 复合问题必须拆成多条查询、指代必须替换、首轮命中就收尾、多来源冲突必须明示、澄清项非空必须追问。
- "这些规则怎么落地的?" → 提示词一律放 `prompts/` 下的 md 文件, 用 `string.Template` 的 `$name` 占位符渲染(因为提示词里有 JSON 花括号, `str.format` 会崩)。

**证据锚点**: `prompts/answer.md` / `prompts/subagents/retriever.md` / `settings/loader.py:12-21` / [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.1。

**常见错误答法**: 说"提示词写得详细一点就行"。关键是**每条规则对应一类失败**, 说得出对应关系才算真做过。
