# 05-工程权衡与踩坑(面试拷打)

> 一句话: 这一篇拷"工程判断" —— 每个设计原则的代价、怎么安全地替换与删除、发现遗留问题后为什么有时故意不修。
> 用法: 先自己答, 再对照"答题骨架"; 深挖追问答不上来就回 [讲解 01 篇](../rag_v01/01-设计构思与关键选型.md) / [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md)。
> 这一篇考察的不是知识量, 而是**取舍意识**: 面试官会顺着你给的方案找代价, 你要先自己说出来。

## Q1. 为什么要把知识库做成"零项目依赖"的独立包?(进阶)

**答题骨架**
两个动机: 一是**可搬走** —— 它不 import 项目里的 `agent/` / `tools/` / `settings/`, 配置自己读 `RAG2_` 前缀的环境变量, 所以它能整目录拷到别的项目里用, 移植时只改调用方; 二是**可测试** —— 边界干净, 单测不依赖项目其他部分, 也不会因为别的模块改动而红。为此还顺带保证"无 import 副作用": 三个对外入口都在函数体内按需 import, 所以 `import rag_v01` 不会拉起 docling/torch、不连库、不建目录。

**深挖追问**
- "代价是什么?" → 它不能直接用项目的配置与数据库连接; `.env` 也不会被它自动加载, 必须由入口负责(命令行用 `uv run --env-file .env`)。
- "怎么验证没有副作用?" → 用**子进程**断言: 导入包之后 `sys.modules` 里不应出现 docling / pymilvus 这些重依赖(同一进程里别的测试早就 import 过了, 进程内看不可信)。
- "为什么配置不直接读 `.env`?" → 读 `.env` 就绑定了项目的配置加载方式; 用环境变量 + 统一前缀, 换成任何宿主都能接。
- "边界怎么守住的?" → 有验收 grep: 包内不得出现 `from agent.` / `from tools.` / `from settings.`。

**证据锚点**: `src/rag_v01/__init__.py`(入口函数体内 import)/ `config.py:11-12` 注释(本文件不读 .env)/ `src/rag_v01/tests/test_cli.py` 的子进程断言 / `pyproject.toml` 的 `known-first-party = ["rag_v01"]`。

**常见错误答法**: 说"为了解耦" 但说不出**代价**(配置要外部注入、`.env` 不自动加载)。只讲好处不讲代价, 面试官会认为你没真正落地过。

## Q2. 为什么整个项目不用 async?(进阶)

**答题骨架**
因为场景是**单用户本地工作台**, 并发来源是"几个子智能体并行", 而不是"成千上万个并发请求"。这种场景下线程池足够, 而异步会渗透到每一层: 数据库驱动、图执行、SSE、工具调用全部要改成 async 版本, 收益不抵复杂度。所以定了硬纪律: 全同步, FastAPI 端点用 `def`(自动走线程池), SSE 用同步 generator, LangGraph 用同步 `stream`, 子图并行靠线程池。**唯一的例外**是 ragas 的嵌入基类强制要求 async 方法, 那几个方法只做"把同步 HTTP 调用丢进线程", 不建事件循环、不改变执行模型。

**深挖追问**
- "异步不是性能更好吗?" → 在高并发 I/O 密集场景是; 这个项目的瓶颈是 LLM API 延迟与单用户交互, 不是连接数。
- "线程池有什么风险?" → 共享可变状态要加锁; 我的 `TaskManager` 用一把锁维护"结果与计数"的账本; 数据库连接非线程安全, 所以并行分支各自取连接。
- "怎么保证纪律不被破坏?" → 有 grep 级验收: 包内不得出现 `async` / `await`(评估适配器那四个方法是有注解的例外)。

**证据锚点**: `src/agent/tasks.py`(线程池 + 单锁账本)/ `AGENTS.md` §五 第 3 条(全同步纪律)/ `evaluation.py` 里那四个 `to_thread` 薄壳的注释。

**常见错误答法**: 说"async 没必要/太麻烦"。要给出**场景判断**: 并发形态是"少量长任务"还是"海量短连接"。

## Q3. 你把知识库内核整个换掉过, 怎么保证不回退?(深水)

**答题骨架**
三个手段叠加: ① **契约先冻住** —— 工具名与 JSON 契约(`doc_id`/`filename`/`seq`/`content`/`score`)一个字不改, 只换实现, 所以上层(子智能体、提示词、去重逻辑)不用动; ② **新旧双跑对比** —— 同一份语料、同一套题、同一个生成器与 judge, 旧系统那侧只经中间产物 jsonl 参与, 不 import 新包, 于是对比是"两个黑盒的成绩单"; ③ **删之前先逐文件哈希比对** —— 我把新目录与旧目录 40 个文件逐个 sha256 比对确认副本完整, 才删掉旧目录。切换动作本身很小(装配处一行 import), 回滚成本接近零。

**深挖追问**
- "怎么保证工具契约不变?" → 契约是**接收方定的**: `_collect_hits` 按 `(doc_id, seq)` 去重, 少一个键就崩, 所以我给适配层写了契约表并在单测里逐字段断言。
- "为什么不改工具名?" → 提示词里写死了 `kb_search`, 而提示词是静态前缀(为前缀缓存), 改名要动提示词并让缓存失效 —— 不值得。
- "旧系统那侧怎么评?" → 一次性脚本用旧实现产出同格式 jsonl(用完即删), 再走「仅评估」入口, 与新技术同台。这是"两段式评估"白送的能力。
- "评审怎么发现回退?" → 双跑报告末尾有并排对比表, 一眼能看到四项指标的方向与幅度。

**证据锚点**: [讲解 01 篇](../rag_v01/01-设计构思与关键选型.md) §四(含 40 题对比表)/ [rag_0.1/07 篇 §4.6.2](../../../new_module/rag_0.1/07-接口设计与移植方案.md)/ `eval_reports/eval_tools_rag_v1_20260922-203552.md` / `ROADMAP §7` 的 2026-09-22 登记条目。

**常见错误答法**: 说"我做了充分测试所以没问题"。**对比数据 + 契约冻结 + 可回滚的最小切面**, 这三样才是可复述的方法。

## Q4. 你怎么判断旧代码可以删了?删之前做了什么?(进阶)

**答题骨架**
先确认三件事: ① **没有调用方** —— 全仓库 grep 出所有引用点, 逐个改完或确认在注释里; ② **能力有替代** —— 旧实现做的每件事在新链路里都有对应(检索、上传、列表、删除、命令行), 并且**保留它唯一还被别人用着的那一块**(向量化客户端被长期记忆复用, 所以留下了); ③ **测试覆盖跟着搬** —— 删模块时不能让"还活着的模块"失去覆盖, 我把保留下来的那个模块的用例搬到了新测试文件。删完再跑全套件确认没有新增失败。

**深挖追问**
- "有什么容易漏的调用方?" → 入口层最容易漏: REPL 命令、HTTP 路由、命令行工具, 它们直调旧实现, 不在检索链路上, 但会 import 就崩。
- "测试怎么处理?" → 旧模块的测试删除(它测的行为不存在了), 但**被保留模块的测试要搬**, 否则覆盖率悄悄掉了。
- "怎么确认没删错?" → 全套件跑一遍, 失败数不增加; 另外有几条外部依赖的失败是长期存在的, 要能分辨(远程沙箱不可达), 不然会把新引入的问题当成老账。
- "文档怎么办?" → 历史开发文档**不改写**, 在头部加一条"已换内核"的转场标注, 指向新的方案文档与契约登记 —— 保留历史真实性的同时不误导读者。

**证据锚点**: `tools/rag/` 现在只剩 `kb_search.py` + `embed.py` / `tests/test_rag_embed.py`(从被删测试里搬过来的两条) / `docs/dev/04-rag/DEV.md` 头部的转场标注 / `ROADMAP §7`。

**常见错误答法**: 说"跑测试通过就删了"。要说清**调用方清单**与**测试覆盖的迁移**, 这是删除类改动的专业度所在。

## Q5. 你踩过的最有价值的一个坑是什么?(开放)

**答题骨架**
我选 jieba 分词那个。现象是: 带空格的查询会返回一批无关结果, 而且分数都差不多。查下去发现 jieba analyzer 把空白和标点也切成 token —— 一个 20 子块的样例里, 2540 个 token 里空格占 1109 个(44%)。**要命的地方在于我用的是 RRF, 只吃名次不吃分数**: 这些噪声 token 让无关子块拿到了真实的名次, 和真命中完全等值, 直接把真命中挤出 top-5。如果我是分数加权融合, 至少还有权重能稀释。修法是给 analyzer 配 138 个停用词表 + 建表自检拦旧表, 并且把验收口径定成"服务端分词与本地 jieba 的差集 ⊆ 停用词表"。这件事教给我的是: **融合方式决定了你要防什么** —— 分数融合怕假高分, 名次融合怕假名次。

**深挖追问**
- "为什么之前没发现?" → 之前用短查询(单词关键词)测的, 噪声票不占优; 是验收时故意用了带空格的短语才暴露。
- "为什么不能改标点 filter?" → 那个 tokenizer 只支持 `stop` 一种 filter, 别的全报不支持, 所以只能靠词表。
- "怎么防止复发?" → 建表自检(抽验空格/换行/"的"三个哨兵) + 验收口径可断言; 改词表必须重建 collection, 这一点也写进了运维手册。
- "还有别的类似坑吗?" → 有, 比如多模态 API 的维度参数写错位置会静默返回默认维度、图片块路径是相对路径不拼根目录会静默退化成文本 —— 共同点是**不报错**。

**证据锚点**: `store.py:52-62`(停用词)/ `_check_analyzer`(228-257)/ [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md) §第 2 组 + "通用教训"。

**常见错误答法**: 讲一个"配置写错了"的坑。要挑**有机制性教训**的(这里: 融合方式与噪声的关系)。

## Q6. 你发现提示词里 `score` 的语义写反了, 为什么没改?(深水, 考工程判断)

**答题骨架**
先说清这件事: 提示词里写"score 越小越相似", 而实现里 RRF 融合分是**越大越相关** —— 方向相反。我没顺手改, 理由是: ① 它**不影响功能** —— 模型不拿这个分数做判断, 工具描述里的这句话只是解释性文字; ② 改提示词会让**静态前缀失效**, 命中率下降, 需要重新验证一轮; ③ 当时正在做内核替换, 属于**不同性质**的改动, 混在同一批里会让"这次改了什么"变模糊; ④ 我的做法是**记录而非隐默**: 写进技术细节手册与本专题的进度文件, 标明"已记录未修, 是否修待定"。

**深挖追问**
- "那你打算什么时候修?" → 下次动提示词时一起(比如调检索纪律), 顺带重跑一轮小样本评估确认没退化。
- "这种'发现了但不修'会不会养成坏习惯?" → 关键是**有人知道**: 记进文档与登记表, 而不是放在脑子里; 否则就是放任。
- "如果它真影响功能呢?" → 那优先级立刻变成最高 —— 判断标准是"是否影响行为", 不是"是否不整洁"。
- "你还发现过哪些遗留问题?" → `RAG2_HF_GEOMETRIC` 只是个未实现的开关位; md 后端的图片恒取不到本体(已按降级处理); 报告里的成本字段"不可用"。三条都标注了状态。

**证据锚点**: `prompts/subagents/retriever.md:10` vs `tools/rag/kb_search.py:16` / [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md) 8.7 / [rag_0.1/TODO](../../../new_module/rag_0.1/TODO.md) 变更登记。

**常见错误答法**: 说"没注意到"。那就说明你不是真读过自己的代码 —— 这题问的就是**你发现之后怎么权衡**。

## Q7. 这条链路上最危险的是什么?你怎么防?(进阶)

**答题骨架**
最危险的是**静默失败** —— 不报错、只是效果慢慢变差, 而且往往在你花了一轮评估的钱之后才发现。典型三种: 向量与文本错位(`zip` 短截长不报错, Milvus 照收)、图片块退化成文本向量(相对路径没拼根目录, 一律判"文件不存在")、多模态维度参数写错位置(静默返回默认维度)。我的防御是**把校验放到写入路径上, 越早越好**: 嵌入阶段拼回时单独校验条数、写库前校验"行数 == 向量数"、建表与检索各一道维度校验、analyzer 用哨兵 token 抽验、超长文本跳过并告警而不是静默截断。

**深挖追问**
- "为什么不在检索时校验?" → 太晚了, 脏数据已经写进库了。
- "为什么超长文本是跳过不是截断?" → 截断会悄悄改变文本内容(可能正好切掉答案), 跳过会留下告警痕迹, 让你的问题可见。
- "有没有量化的兜底?" → 有: 真机冒烟里把两路分数与手算的 RRF **逐条比对**, 一旦错位立刻暴露; 评估则是第二道防线。
- "通用原则?" → 凡是"错了不报错"的地方, 都要主动断言; 宁可能误报, 也不要漏报。

**证据锚点**: [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md) 第 3 组 + 通用教训第 1 条 / `embed._place` / `store.upsert_children` 的行数校验。

**常见错误答法**: 说"加日志和监控"。静默失败**不会留下异常**, 只能靠断言与自检提前拦住。

## Q8. 为了评估单独开一个依赖环境, 值得吗?(进阶)

**答题骨架**
值得, 但这是**成本换隔离**的选择。原因是硬冲突: ragas 0.4 经 instructor 要求 `rich<15`, 主项目钉 `rich>=15`。两条出路: 主项目放宽 rich, 或者另建环境。我选了后者 —— 主项目的 `pyproject.toml` 与锁文件**一个字节都没动**, 代价是多维护一个 uv 项目与一次环境级依赖覆盖。为了让它更好用, 评估侧只吃中间产物 jsonl, 所以"检索 + 生成"这一半在主环境就能跑, 只有打分那一步需要在评估环境。

**深挖追问**
- "多维护一个环境有什么风险?" → 版本漂移: 评估环境的库升级可能改变分数, 所以报告 meta 里记了 ragas 版本、judge 型号、参数快照, 便于以后对齐。
- "为什么不干脆把主项目降级 rich?" → 那会让主项目所有依赖跟着变(实测放宽 rich 会连锁降 openai 的版本), 影响面大得多, 而收益只是"少一个环境"。
- "还踩了什么坑?" → 评估环境里没有可用的 torch(CUDA DLL 起不来), 所以命令行必须按子命令**懒加载**, 否则 `evaluate` 命令自己就起不来。
- "有更省事的方案吗?" → 有: 把评估写成独立脚本 + 自带 venv, 但那样就失去了与线上检索同源的保证(评估要真跑检索与嵌入)。

**证据锚点**: `eval/pyproject.toml` 的 `override-dependencies` 与路径依赖 / [讲解 06 篇](../rag_v01/06-评估工程实现.md) §四 / 主项目 `pyproject.toml`(未改动)。

**常见错误答法**: 说"我用了 Docker/conda 隔离"。要讲清**冲突的具体来源**(rich 版本)与**隔离的边界**(只隔离打分那一步)。
