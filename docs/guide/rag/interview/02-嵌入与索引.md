# 02-嵌入与索引(面试拷打)

> 一句话: 这一篇拷"向量与索引这条路的底层选择" —— 模型选型、相似度度量、索引参数、以及被 Milvus 与 jieba 硬约束坑过的几处。
> 用法: 先自己答, 再对照"答题骨架"; 深挖追问答不上来就回 [讲解 02](../rag_v01/02-入库侧全链路.md) / [讲解 03](../rag_v01/03-检索侧全链路.md) / [讲解 07](../rag_v01/07-技术细节与坑位手册.md)。

## Q1. 向量库为什么选 Milvus, 不用 pgvector?(基础)

**答题骨架**
核心原因是**稀疏检索下推**。Milvus 2.6 内置了 BM25 Function 与 jieba analyzer: 入库存原文, 服务端自动生成稀疏向量并建倒排索引, 检索时 query 原文直传。如果留在 pgvector, 就得在客户端自己维护一份 BM25 索引(我上一版系统就是这么做的: 内存索引 + 脏标记重建), 多一份状态、多一处不一致风险。另外 Milvus 的向量索引能力(HNSW 参数可调、稀疏倒排)也比 pgvector 强。代价是开发机要多起三个容器(etcd/minio/milvus)。

**深挖追问**
- "pgvector 不是能复用现有的 PostgreSQL 吗?" → 能, 省一个服务; 但它给不了服务端稀疏索引, 混合检索要自己拼 SQL 与客户端索引。
- "换库的代价是什么?" → 数据要重灌(嵌入模型也从纯文本换成多模态了, 向量不可比), 运维多一套 compose。
- "为什么不用 Chroma / FAISS?" → 本地文件型方案简单, 但没有稀疏路, 我要的能力要自己再搭一套。

**证据锚点**: `src/rag_v01/store.py` 的两个 collection 定义 / [讲解 01 篇](../rag_v01/01-设计构思与关键选型.md) §2.3 的候选与否决理由表 / Milvus 跑在 WSL docker, 19530。

**常见错误答法**: 说"Milvus 性能更好" —— 这个数据规模下性能不是理由; 真正的理由是**能力**(内置 BM25)与**可解释性**。

## Q2. 为什么用多模态 embedding? 我用纯文本行不行?(进阶)

**答题骨架**
因为我的解析阶段会把 pdf 里的插图单独落盘成图片块。如果 embedder 只能吃文本, 这些图片块就只能拿一句占位文本去算向量 —— 等于图片白提取了, 检索时图片内容完全不可达。我用的百炼 `qwen3-vl-embedding` 把文本和图片嵌进**同一个向量空间**, 实测"图片与它的相关描述文本"的余弦相似度是 0.7444, 而"图片与无关文本"是 0.2282, 差得很开, 说明同空间这个前提是成立的。

**深挖追问**
- "怎么验证同空间?" → 就是上面那组对比数; 这是入库前必做的一次真机验证, 不做的话你不知道图片向量是不是"乱猜的"。
- "纯文本场景怎么办?" → 可以换纯文本模型(更便宜), 但图片块就只能走文本降级; 我留了 local bge-m3 作离线备选。
- "多模态有什么代价?" → 依赖外部 API、图片要转 data URI 上传(单图 ≤10MB)、批量上限更小(文本 20 条 / 图片 5 条)。

**证据锚点**: `src/rag_v01/embed.py` 的 `_ApiBackend` / `_to_data_uri` / 跨模态实测 0.7444 vs 0.2282 记录在 [rag_0.1/04 篇](../../../new_module/rag_0.1/04-嵌入与Milvus索引.md) §五。

**常见错误答法**: 说"因为多模态更先进"。要说清**你的语料里有图片块**, 不做多模态就有块没向量。

## Q3. 向量为什么会做 L2 归一化? 有什么影响?(基础)

**答题骨架**
我的度量是余弦相似度, 归一化对**排名本身没有影响**(余弦本来就忽略模长)。做归一化的目的是三个: 两个后端(API 与本地)尺度一致、分数落在 [-1, 1] 这种可读区间、以及以后换 IP 或内积度量时排名不变。零向量不参与除法。

**深挖追问**
- "那不做行不行?" → 行, 但你要放弃上面的好处; 而且不归一化时"分数绝对值"会随文本长度漂移, 排障时容易误判。
- "余弦和内积有什么区别?" → 内积受模长影响, 归一化后两者等价。

**证据锚点**: `embed.py:36-45`(`_l2_normalize`, 注释写了"对 COSINE 排名无影响")。

**常见错误答法**: 说"归一化是为了提高相似度准确率"。它不是精度手段, 是**尺度一致性**手段。

## Q4. HNSW 的 M、efConstruction、ef 分别是什么?你要调哪个?(进阶→深水)

**答题骨架**
三个参数分两个阶段: `M`(每个节点的邻居数)与 `efConstruction`(建索引时的候选队列宽度)是**建索引期**的, 决定图的质量与构建成本, 我固定 `M=16 / efConstruction=200`; `ef` 是**查询期**的搜索宽度, 决定召回率与延迟的平衡。要调就调 `ef`, 因为它不进索引、改了立即生效。不过实测在我的数据规模上 `ef` 取 64/96/128 结果**20/20 完全一致** —— 语料只有几百个子块, 图很浅, 64 已经够搜到真近邻了。

**深挖追问**
- "为什么不调 M?" → 它要重建索引, 而且收益要看规模; 几百个子块谈不上图质量瓶颈。
- "ef 调大的代价?" → 查询延迟线性上升(要访问更多候选)。
- "什么时候 ef 才有意义?" → 百万级向量、图深的时候; 这说明**调参要按自己的数据规模判断, 不能照搬经验值**。

**证据锚点**: `store.py:42-43`(`_HNSW_M=16` / `_HNSW_EF_CONSTRUCTION=200`, 注释标注"ef 是查询期参数, 不在索引里") / `config.py` 的 `hnsw_ef=96` / 三档实测 20/20 一致, 见 [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §三。

**常见错误答法**: 把三个参数混为一谈, 或说"ef 越大越好"。能讲清"建索引期 vs 查询期"就已经过关。

## Q5. Milvus 建表有没有把你坑过?(深水)

**答题骨架**
有四条硬约束是踩出来的: 一是 collection **必须至少有一个向量字段**; 二是**每个向量字段都必须有索引**才能 load; 三是向量字段**不支持 nullable**; 四是**维度下限是 2**。这四条合起来逼出了一个反直觉设计: 我的 `parents` 表只存文本、本来不需要向量, 但为了满足前两条, 只能加一个 dim=2 的零向量占位 + FLAT 索引, 每行多 8 字节, 换"这张表能存在"。另外 `page_no` 这种可能缺失的标量列也不能写 null, 我用 -1 当哨兵, 检索时再还原成 `None`, 并且只在两处转换。

**深挖追问**
- "为什么 parents 和 children 要分两个表?" → 检索命中子块, 但上下文要给父块; 父子字段与索引需求不同(子块要向量 + BM25, 父块只要主键点查), 混一张表会让 schema 变复杂。
- "占位向量会不会影响检索?" → 不会, 那个字段从不参与检索, 只是满足 load 条件。
- "还有什么隐藏约束?" → VARCHAR 上限按**字节**算(中文约 3 字节/字), 所以超长文本的判据要用 `encode("utf-8")` 比长度; 我的处理是**跳过并告警**, 不静默截断。

**证据锚点**: `store.py:6-14`(四条实测事实的注释) / `_parent_schema` + `_parent_index` / `store.py:402` 与 `retrieve.py:174-181` 的 `-1` 哨兵双向转换。

**常见错误答法**: 说"没遇到什么约束"。这四条是真实踩出来的, 能讲出来说明你真动过 Milvus。

## Q6. 内置 BM25 的分词把你的检索质量弄坏过?怎么解的?(深水)

**答题骨架**
坏了, 而且这个坑挺有教学价值。jieba analyzer 会把**空白和标点也当成 token** —— 我统计过一个 20 子块的样例, 2540 个 token 里空格占 1109 个(**44%**)。要命的是我用的是 RRF, **只吃名次不吃分数**: 带空格的 query 让这些噪声 token 命中一批无关子块, 它们拿到的名次和真命中**完全等值**, 直接把真命中挤出 top-5。如果换成分数加权融合, 至少还能被权重稀释; 名次融合没有这道缓冲。

对策是给 analyzer 配 138 个停用词表, 并加一道**建表自检**(抽验空格/换行/"的"这几个哨兵 token)拦住旧表 —— 因为 analyzer 是建表时写进 schema 的, 改词表必须 drop 重建 + 重灌。顺带发现: 那个 tokenizer **只支持 `stop` 这一种 filter**, `removepunct`/`length`/`lowercase` 全都报不支持, 所以标点治理也只能靠停用词表。

**深挖追问**
- "怎么确认修好了?" → 验收口径是可断言的: 服务端 `run_analyzer()` 的 token 与本地 `jieba.lcut_for_search(HMM=True)` 的**差集 ⊆ 停用词表**。
- "为什么不自建 BM25 索引而要受这个气?" → 自建的代价是客户端多一份需要重建的状态; 现在这份代价换成了"改词表要重灌", 由我在流程里承担, 而不是长期维护两份不一致的索引。
- "这个坑的通用教训?" → **融合方式决定了你要防什么**: 分数融合怕假高分, 名次融合怕假名次。

**证据锚点**: `store.py:52-62`(停用词表)/ `_analyzer_params`(89-96)/ `_check_analyzer`(228-257) / [讲解 03 篇](../rag_v01/03-检索侧全链路.md) §4.2 / [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md) 第 2 组。

**常见错误答法**: 说"分词问题我用了更好的分词器"。真答案是**融合方式放大了分词噪声**, 换分词器只是换一批噪声。

## Q7. 如果我改了 embedding 维度或模型, 要做什么?(进阶)

**答题骨架**
要**重建两个 collection 并重灌全部语料**, 原因有两层: 表结构里向量维度是写死的(改维度必须重建表), 而且换模型就是换向量空间 —— 旧向量留在库里没有意义, 检索出来的是"两个不同空间的距离"。我在三处做了维度校验(建表自检、嵌入输出自检、检索期一致性), 报错文案里直接点明环境变量名和"改维度必须重建 collection"。语料重灌本身不贵(500 篇约 2 分钟), 贵的是一切评估报告失去可比性, 所以要重跑基线。

**深挖追问**
- "怎么保证重灌后没有新旧两份?" → doc_id 是内容寻址的, 同源文件重灌时 `purge_stale` 会先清掉旧 doc_id 的版本 —— 顺序必须在写入**之前**, 否则会把自己刚写的删掉。
- "不重灌会怎样?" → 检索可能报维度错, 或者(如果维度碰巧相同)静默返回无意义的结果 —— 这属于最坏的一类失败。
- "评估上怎么处理?" → 重建基线, 并更新报告里的参数快照; 旧报告不能再与新数据对比。

**证据锚点**: `embed._check_dim` / `store._check_children` / `store.purge_stale`(528-552)/ `pipeline.py:94-98` 的调用顺序 / [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §四。

**常见错误答法**: 只说"重新索引一下就行"。维度与模型两个变化都会让旧向量**语义上作废**, 不是重建索引的问题。

## Q8. 怎么发现"向量和文本错位了"这种静默错误?(深水)

**答题骨架**
这类错误最阴: 它不报错, 只是效果慢慢变差, 而且你发现时可能已经花了一轮评估的钱。我的防御是三处主动校验, 都在数据进入 Milvus **之前**: ① 嵌入阶段把文本/图片分组调用后**按原下标拼回**, 拼回时单独做一次条数校验(因为 `zip` 在长度不等时是短截长、不报错, 只会整体错一格); ② 写库前再校验"行数 == 向量数", 不等直接抛; ③ 检索期做维度与一致性检查。另外我还把"图片块静默退化成文本向量"这个具体的坑记在代码注释里: `image_path` 是相对路径, 判存在前必须先拼 `RAG2_IMAGE_DIR`, 否则所有图片块都会走文本路而且没有任何报错。

**深挖追问**
- "为什么不在检索时校验?" → 太晚了, 数据已经写进去了; 校验点要放在**写入路径上**, 越早越好。
- "还有哪些同类静默失败?" → 维度参数写错位置(多模态 API 的 `dimension` 必须走顶层 kwarg, 写进 `parameters` 会静默返回默认的 2560 维)、analyzer 带着脏词表跑、超长文本被跳过。
- "怎么验证修好了?" → 用固定语料跑一次入库 + 检索, 断言命中与手算一致(我是手算 RRF 逐条比对)。

**证据锚点**: `embed._place`(262-272)/ `store.upsert_children`(375-408)的"行数≠向量数直接抛" / `embed._image_file`(76-85)/ [讲解 07 篇](../rag_v01/07-技术细节与坑位手册.md) 第 3 组与"通用教训"第 1 条。

**常见错误答法**: 说"加日志/监控就能发现" —— 这类错误不会留下日志(没有异常), 只能靠**断言与自检**提前拦住。
