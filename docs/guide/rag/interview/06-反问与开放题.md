# 06-反问与开放题(面试拷打)

> 一句话: 这一篇是"没有标准答案"的部分 —— 反问面试官的话术, 以及短板、扩展、如果重做这类开放题; 答这类题靠的是**有取舍的路线图**, 不是堆功能名词。
> 用法: 反问话术可以背; 开放题请按"先说现状约束 → 再说改什么 → 最后说代价"三段式组织, 别只列 todo。
> 相关: [讲解 08 篇](../rag_v01/08-调参与容量手册.md)(容量与调参)、[rag_0.1/07 篇](../../../new_module/rag_0.1/07-接口设计与移植方案.md)(被否决的方案与触发条件)。

## 一、反问面试官(3~5 个, 挑场合用)

### R1. "你们现在的检索是纯向量还是混合?召回率主要在哪个环节丢?"

**为什么问这个**: 表明你知道混合检索与"召回 vs 排序"的分层, 而不是只会调 API。同时**能听到他们的技术栈**, 方便后面答得贴题。

**追问** → "有没有做 rerank?如果做, 是在检索内还是生成前?"

### R2. "你们的评测集是人工标注还是模型生成?噪声是怎么处理的?"

**为什么问这个**: 这是 RAG 团队最真实的痛点; 我这边量出过噪声带(判分侧 Δ0.09~0.20), 一问就能接上自己的经验。

**接话** → "我这边做过一个复现性实验, 固定输入重跑评估时检索侧 Δ=0 而 faithfulness 抖 0.20, 所以定了'差异小于 0.1 不下结论'的纪律。"

### R3. "这套系统是给单机自用还是多租户?增量更新和权限是怎么处理的?"

**为什么问这个**: 直接暴露"有没有生产经验"的分界线 —— 我目前的实现是单用户本地、内容寻址 + 全量重灌, 增量与权限是真缺口。

**接话** → "我这边是单用户本地, 内容寻址 + 同源清理, 改分块就要重灌; 多租户需要加会话归属和 namespace 隔离。"

### R4. "团队现在更缺'把效果量化出来'还是'把延迟降下来'?"

**为什么问这个**: 问**优先级**, 顺带表达"我知道这两件事要做的取舍不一样"。

### R5. "如果我进来, 前三个月最想让我接手哪一块?"

**为什么问这个**: 把话题从"我做过什么"转到"我能为你们做什么", 也是收尾的好问题。

**不要问的**: 太泛的("你们的技术栈是什么"——JD 里写了)、太功利的(加班/转正直接问, 语气全崩)、以及**假装懂而问的**(问了接不住更糟)。

## 二、开放题

### O1. 这套系统最大的短板是什么?(开放)

**答题骨架**
我会说三个, 按严重程度排: ① **多用户与权限**完全没做 —— 库是本地单用户、文档没有归属概念, 而真实的团队知识库一定需要按人/按部门隔离; ② **增量更新粒度粗** —— doc_id 是内容寻址, 文件改一个字就是一份新文档, 我靠"同源清理 + 整篇重灌"处理, 没有做块级增量(改一节不用重嵌整篇); ③ **评估覆盖不全** —— 语料是一段一文件, 父子分块的多子块/跨页能力**没有被评估覆盖**, 只有单测与真 pdf 人工核对。另外还有一个已知的工程债务: 答案里的引用没有做逐句校验, `sources` 只是文档级列表。

**深挖追问**
- "哪个最容易补?" → ③ 可以靠换一份结构化语料 + 扩充测试集补; ① 要在存储层加归属字段, 改动面大; ② 需要引入块级哈希与差量更新。
- "有没有你其实能做但没做的?" → 有: rerank、查询改写模块、答案级引用校验。不做是因为**当前评估噪声带是 0.1**, 加了也证明不了有效, 属于"无法验证的复杂度", 我宁可先不引入。
- "为什么不先做这些?" → 单机自用场景下它们不是瓶颈; 我把时间花在了把链路做对(可解释、可复现、能替换)上。

**证据锚点**: [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §六(盲区)/ [讲解 01 篇](../rag_v01/01-设计构思与关键选型.md) §五(被否决备选的触发条件)。

### O2. 如果给你一个月, 你会怎么改?(开放)

**答题骨架**
我按"先让评估更可信, 再改系统"排序, 因为**评估不可信时所有改动都是盲改**:

| 优先级 | 做什么 | 为什么排这个位置 | 代价 |
|---|---|---|---|
| 1 | 扩测试集到 200 题 + 换一份有层级结构的语料(技术文档/手册) | 现在 40 题只能看量级差异, 且覆盖不到多子块/跨页 | 标注或自动生成 + 人工抽检, 评估时间涨 5 倍 |
| 2 | 生成结果缓存 + 按 (question, contexts) 复用, 让"仅评估"成为常规回归 | 现在改一个参数就要重跑 32 分钟且带噪声 | 一个缓存层的工程量 |
| 3 | 加 rerank(交叉编码器), 用真实语料验证 top-20 → top-5 的增益 | 评估可信之后才能证明它有效 | 模型推理延迟与成本 |
| 4 | 块级增量更新 | 真实使用中改文件很频繁 | 需要设计块级哈希与差量流程 |
| 5 | 答案级引用校验(每句引用到 chunk) | 提升可信度与可追溯性 | 需要额外的对齐逻辑 |

**深挖追问**
- "为什么不先做 rerank?" → 现在评估噪声 0.1 量级, rerank 通常带来 0.03~0.08 的提升, 在这个噪声下根本测不出来 —— 先修尺子再量东西。
- "扩测试集钱从哪来?" → 用现有语料自动出题 + `answer_start` 自动校验 + 人工抽检一部分, 成本可控。
- "一个月够吗?" → 前三项实际; 4/5 会溢出到下一个周期。

**证据锚点**: [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.2(噪声带)/ [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §六(实验方法)。

### O3. 多用户/多租户要怎么改?(开放)

**答题骨架**
分两层: **存储隔离**与**语义隔离**。存储上, Milvus 支持在集合里加标量字段做过滤, 所以先给所有行加 `tenant_id` 并把它写进查询 filter; 更彻底的做法是每个租户一个 collection 或 partition(隔离性更好, 但运维复杂度上升)。语义上, 会话归属是另一件事: 谁上传的文档、谁能检索, 需要在关系库里维护一张归属表, 而不是靠向量库的过滤兜住全部权限。另外内容寻址会带来一个跨租户的坑: 如果两个租户上传同一份文件, 内容 hash 相同 → 同一个 doc_id, 这时候"谁拥有它"就必须由归属表回答, 不能让内容 hash 兼任身份。

**深挖追问**
- "为什么不用 namespace 隔离?" → 如果需要的是"同一份数据按视图过滤", 加字段更快; 如果是"完全互不可见 + 计费隔离", 一租户一 collection 更省心。
- "内容寻址的坑怎么解?" → 把 doc_id 保持为内容身份, 另设 `doc_owner` 关系表; 或者把租户 id 混入哈希(牺牲跨租户去重换简单)。
- "评估侧要改吗?" → 要: 测试集与报告也要带租户维度, 否则你不知道指标是哪个租户的。

**证据锚点**: 现状: `store.py` 的 filter 能力(加标量字段即可)/ 内容寻址定义见 `parsers/common.py:33-39` / 契约变更要回登 `ROADMAP §7`。

### O4. 增量更新: 用户改了文档的一节, 你怎么处理?(开放)

**答题骨架**
现状是"整篇重灌": 内容寻址让改过的文件有一个新 doc_id, 入库时按 `source` 清掉旧版本(`purge_stale`), 所以**不会有两份**, 但也没省算力 —— 整篇会重新解析、切分、嵌入。要做到块级增量, 需要: ① 稳定的块级身份(不能是内容 hash, 否则改一个字整块就换身份了, 应该用"文档 id + 结构路径/序号"这种**位置身份**); ② 新旧块做集合差(增删改); ③ 只嵌入变化的部分; ④ 删除时按身份精确删。难点在"结构路径"的稳定性: 标题改了、段落插删会让后续序号漂移, 这部分要靠内容哈希做二次匹配来减少误判。

**深挖追问**
- "为什么不用内容 hash 当块身份?" → 那样改一个字就是"删一块 + 加一块", 差的块少时无所谓, 正文段落微调会让整节重嵌。
- "删除怎么保证干净?" → 现在的删除是按 doc_id 整删(逻辑删除 + 过滤), 块级删除需要 `chunk_id` 级过滤, Milvus 支持, 但要处理"删了又立刻查"的可见性。
- "值得做吗?" → 文档更新频繁时值得; 现在这个规模的语料整篇重灌只要 2 分钟, 优先级低。

**证据锚点**: `store.purge_stale`(528-552)/ `parsers/common.py` 的 `compute_doc_id` / [讲解 02 篇](../rag_v01/02-入库侧全链路.md) §6.3。

### O5. 如果文档涨到百万级, 架构要改什么?(开放)

**答题骨架**
现在的设计里有几处在百万级会成瓶颈, 我会按顺序改: ① **入库改成批量并行 + 断点续跑**(现在是逐文件串行, 峰值内存好看但吞吐低; 百万级要分片并行, 并用任务表记录进度); ② **`list_docs` 改成维护一张文档汇总表**(现在是全量拉子块在客户端聚合, 因为有"Milvus 没有 GROUP BY"); ③ **索引参数重调** —— `M/efConstruction/ef` 在这个规模才真正有意义(现在实测 `ef` 完全不敏感, 就是因为库太小); ④ **稀疏路与向量路分服务或分片**, 并引入 rerank 做精排; ⑤ **评估改成抽样 + 在线指标**(全量 ragas 在百万级不可行)。

**深挖追问**
- "为什么要维护汇总表?" → 现在 `list` 的成本是"子块总数", 百万级会到千万行, 客户端聚合不可接受。
- "分块策略要变吗?" → 可能要: 百万级文档的形态更杂, 可能需要按文档类型走不同分块参数。
- "还有什么会先崩?" → 单机 Milvus 的内存与段合并; 需要独立部署与容量规划。

**证据锚点**: `store.list_docs`(502-526, 注释写明"运维动作, 非检索热点") / [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §五(容量估算: 1024 维 ≈ 4KB/行)。

### O6. 成本怎么优化?(开放)

**答题骨架**
先分清成本构成: **入库时**是 embedding 调用(全量重灌一次约 2 分钟、按量计费), **问答时**是生成 + (如果有)rerank, **评估时**是生成 + 判分的大头。优化按收益排: ① **评估侧缓存**生成结果, 只重跑判分或只跑被测那一半 —— 直接省掉一半以上; ② **减少无谓重灌**: 把"哪些参数改了必须重灌"写进手册(我是这么做的), 避免全量重嵌; ③ 入库用**批量 + 去重**(内容寻址天然去重, 同一文件重复上传零成本); ④ 检索侧 **先粗后精**: 候选深度别一上来开到 50, 用 RRF 的 top-5 就够; ⑤ 生成本身可以用小模型先在评估里筛, 大模型只用于最终回答。

**深挖追问**
- "评估为什么最贵?" → 40 题跑一遍 32 分钟, 每题要生成 + 四个指标判分(部分指标还要再生成一轮问题)。
- "能省到什么程度?" → 固定输入只重跑判分, 或按 (question, contexts) 复用生成, 能省掉生成那一半; 剩下的是判分, 那是 ragas 的固有成本。
- "降本会和什么冲突?" → 和统计置信度冲突: 题量变少、轮次变少, 噪声带更宽, 你能下结论的阈值更高。

**证据锚点**: [讲解 06 篇](../rag_v01/06-评估工程实现.md) §七(耗时与费用, 含"费用统计未接"这一缺口)/ [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §四(重灌条件)。

### O7. 如果让你重做一遍, 你会改什么?(开放)

**答题骨架**
三件事: ① **从第一天就把评估和缓存建起来** —— 我是先把链路做通再补评估, 结果中途想验证效果时只能"感觉", 还因为 judge 的噪声差点把结论做错; ② **语料选型更早介入** —— 我用的评估语料是一段一文件, 覆盖不到父子分块最核心的能力, 如果一开始就用有层级的文档, 评估的结论会更有说服力; ③ **把"必须重灌的条件"当成配置的一部分管起来** —— 我后来才把它写成手册, 更靠前的做法是让配置项自己带元数据(改了要重建/重灌), 由代码来提示而不是靠人记。

**深挖追问**
- "有哪件是你现在觉得很对的?" → 契约先冻住再换实现、双跑对比、静默失败主动断言 —— 这三条让我在换整个内核时没有回退。
- "教训是什么?" → **先修尺子再量东西**: 评估基础设施的优先级应该高于任何单个算法改进。
- "重做会更快吗?" → 会: 现在这套文档本身就是重做时的路线图(每一篇都写了"当时怎么想、坑在哪")。

**证据锚点**: 本专题 [讲解 00 篇](../rag_v01/00-全链路总览.md) 的证据索引 / [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §5.4(评估事故)/ [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §四。

## 三、收尾: 开放题的三段式模板

任何"你会怎么做"的问题, 按这个顺序答, 比列一堆技术名词得分高:

```text
① 现状与约束: 我这个系统现在是什么样、瓶颈在哪、为什么当时这么选
② 改什么: 按优先级给 2~3 项, 每项一句"为什么排这个位置"
③ 代价: 每项要付什么(工程量 / 成本 / 精度或延迟的取舍 / 数据要重灌)
```

**切记**: 说"不做"的时候要给理由(比如"加了也验证不了, 因为评估噪声带是 0.1"), 这类回答比"我全都想做"更能体现判断力。
