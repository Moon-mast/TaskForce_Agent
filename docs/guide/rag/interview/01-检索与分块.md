# 01-检索与分块(面试拷打)

> 一句话: 这一篇拷的是"检索链路的设计与实现" —— 为什么这么切、为什么这么融合、出了问题怎么定位。
> 用法: 先自己答一遍, 再看"答题骨架"对照; "深挖追问"是面试官顺着的第二、三层, 答不上来就回 [讲解篇](../rag_v01/03-检索侧全链路.md)。
> 证据锚点里的文件路径都在本仓库, 面试时不用报路径, 但**数字要能说出来**。

## Q1. 你的知识库检索是怎么做的?(基础)

**答题骨架**
我做的是一条混合检索链路: 文档先按父子两层切分, 检索时用**子块**同时在**向量路**和**BM25 关键词路**各取 20 个候选, 用 RRF 按名次融合, 取 top-5 后**回溯到父块**作为喂给模型的上下文, 最后按父块去重。检索不是一次函数调用, 而是包在一个 ReAct 子智能体里, 它可以用不同措辞多试一两次。

**深挖追问**
- "为什么不直接用向量?" → 向量对专有名词、型号、代码标识符不稳; BM25 正好补这个, 两条路互补。
- "两路结果怎么合?" → 按名次融合(RRF), 不是按分数加权 —— 两条路的分数量纲不可比。
- "回溯父块是什么?" → 子块只用来"找到位置", 真喂模型的是它所属的父块全文。

**证据锚点**: `src/rag_v01/retrieve.py`(编排 97-141 行) / `rrf_fuse`(40-87 行) / 双路各 `candidate_top_n=20`。

**常见错误答法**: 只说"用了向量数据库做相似度检索", 说不出混合检索与父块回溯 —— 这是这个项目最核心的两个设计, 答不出来等于没讲。

## Q2. 为什么用父子分块, 而不是固定长度切?(基础)

**答题骨架**
因为**检索要窄、生成要宽**。固定 500 字切片里, 向量被多个主题稀释, 检索命中率低; 但只把 500 字喂给模型, 它拿到的可能是半句话。我用小到 450 字的子块去检索, 命中后回溯它所属的 1200~1800 字的父块作为上下文。这样两个粒度各自最优。

**深挖追问**
- "父块怎么切?" → 沿 docling 解析出的**标题层级**聚合, 不是按字数硬切; 遇到同级或更浅的标题就闭合, 将超上限时闭合。
- "标题要不要放进正文?" → 要。因为 BM25 只索引正文文本字段, 标题里的词是最强的检索信号。
- "表格和图片呢?" → 原子块, 不切, 独占一个父块。
- "效果怎么验证的?" → 单测 21 项 + 真 pdf 人工核对(15 页讲义、156 条目全部带页码); 评估语料一段一文件、覆盖不到多子块场景, 这点我会主动说明。

**证据锚点**: `src/rag_v01/chunk/parents.py` 三条聚合规则(31-80 行) / `chunk/__init__.py:71` 的 `parent_id` 格式 / 评估语料盲区见 [讲解 05 篇](../rag_v01/05-质量检验策略与方法.md) §六。

**常见错误答法**: 说"父子分块能提升召回 30%"——**没有这个证据**。评估语料覆盖不到这个能力, 老实说"靠单测与真 pdf 验证"反而加分。

## Q3. 父块 1500 字、子块 450 字、重叠 50, 这些数怎么定的?(进阶)

**答题骨架**
先说口径: 1500 是**目标值**, 实际达标区间是它的 0.8~1.2 倍即 1200~1800; 而且**下限只用于统计达标率, 不作为切分约束** —— 短节就该产出小块, 硬凑会把两节混在一起。450/50 来自两个约束: 子块要能装下一个完整语义单元(一两段话), 重叠要够跨越"答案被切在边界"的情况。这些值一改就要重灌语料, 所以我用**真 pdf 量了块长分布**再定, 而不是拍脑袋。

**深挖追问**
- "为什么下限不做约束?" → 真实文档里有大量短节; 强行凑块会造成跨节污染, 比块小更糟。
- "达标率是验收标准吗?" → 不是。实测 37 个真 pdf 父块只有 1 个落在达标区间 —— 结论是"达标率是文档形态的函数", 它只能用来发现异常(比如全语料 0%), 不能当门槛。
- "改这些数会有什么后果?" → 必须重灌, 而且此前所有评估报告失去可比性。

**证据锚点**: `chunk/parents.py:19-28`(`PARENT_MIN/MAX_RATIO = 0.8/1.2`) / 真 pdf 分布记录见 [rag_0.1/TODO](../../../new_module/rag_0.1/TODO.md) / 重灌条件见 [讲解 08 篇](../rag_v01/08-调参与容量手册.md) §四。

**常见错误答法**: 说"这是业界最佳实践"——你实际做过实验, 说实验更实在; 也别说"下限是硬约束", 代码里不是。

## Q4. 子块的重叠为什么自己写?(进阶)

**答题骨架**
因为我用的是 langchain 的 `RecursiveCharacterTextSplitter`, 它的 `chunk_overlap` 是按**整片文本**量化的, 实际落点会在 30 上下或 70 多这种量级, 做不到我要的 40~50。所以我把它的重叠关掉(`chunk_overlap=0`), 自己取上一块尾部的字符窗口, **再回退到句界**; 对齐后的长度不够(比窗口少超过 10 个字符)就干脆取整窗, 宁可重叠多一点, 也不要在句子中间截断。

**深挖追问**
- "重叠是干什么的?" → 防止答案正好被切在块边界, 两边都只拿到半句。
- "为什么不用库的?" → 库按片量化, 做不到稳定区间; 另外库会把分隔符贴到下一片开头, 得手动搬回上一片尾(不然子块开头多出标点、闭引号被切开)。
- "上一块本身很短怎么办?" → 不重叠。整块复制是纯噪声。

**证据锚点**: `src/rag_v01/chunk/children.py` 的 `_splitter`(35-51 行)、`add_overlap`(77-105 行)、`_OVERLAP_TOLERANCE=10` / 单测锁 40~50 区间。

**常见错误答法**: 说"重叠用的是库默认值"——这个项目的重叠是手写的, 这是能体现"你真读过库行为"的细节。

## Q5. RRF 是什么?为什么 k 取 60?(基础+进阶)

**答题骨架**
RRF 是 Reciprocal Rank Fusion: 每个候选取它在各路的名次, 分数是 `Σ 1/(k + rank)`, 按总分排序。它的好处是**只用名次不用分数**, 所以两条量纲不同的路(余弦相似度 vs BM25 分)不需要归一化就能合。`k=60` 是常用值, 它的作用是把名次差压缩进分母 —— `k` 越大, 第 1 名和第 20 名的贡献越接近, 融合越像"投票"; `k` 越小, 靠前的名次越占绝对优势。我没有对 `k` 做调参, 实测真正敏感的是候选深度。

**深挖追问**
- "还有别的融合方式吗?" → 分数加权(要先归一化, 且分布敏感)、Milvus 原生 `hybrid_search` 的 RRFRanker(一行搞定, 但拿不到中间名次)。
- "为什么不用原生的?" → 我保留每个结果在两条路的**名次**, 评估归因时能回答"这题没答对是 dense 没召回还是 sparse 没召回"; 用原生融合这个信息就丢了。这是拿可解释性换一行代码。
- "RRF 有什么坑?" → 名次要**从 1 起**、同分要按 id 兜底(否则顺序随机、回归不可复现)、要先排序再 round(先 round 会抹平名次)。

**证据锚点**: `retrieve.py:40-87`(含同分兜底与先排序后 round) / 真机冒烟手算 `1/(60+r_d)+1/(60+r_s)` 与实现**逐条相等** / 30 项单测。

**常见错误答法**: 把 RRF 说成"加权求和"——那正是它要避免的东西; 或者说"k 越大越好", 没有这种事。

## Q6. 两路各取 20 个候选, 20 是怎么来的?(进阶)

**答题骨架**
先看实验: 我把候选深度从 20 调到 50, 20 道题里 **11 道的 top-5 结果发生了变化** —— 说明这个旋钮确实动得了结果, 不是摆设。20 的选择是"够深但不过分"的折中: 再深会在融合阶段引入更多低质候选(它们在单路里名次很靠后, 但 RRF 会给它们票), 而且深召回意味着更多的向量检索开销。真正的上限应该由评估来定, 我这套评估的噪声带是 0.1, 所以能做的是看**逐题变化**(11/20)而不是均值微差。

**深挖追问**
- "为什么不索性取全库?" → RRF 会给所有出现过的候选投票, 候选越多噪声票越多; 而且延迟与内存都上去了。
- "怎么判断 20 是否合适?" → 固定中间产物跑「仅评估」对比 precision/recall, 看逐题差异; 均值差 0.01 在噪声里, 不能作为依据。
- "还有别的旋钮吗?" → `retrieve_top_k`(5), 但它往下受 answer 侧的截断闸门限制(4 条 / 1200 字), 多拿了也可能被截掉。

**证据锚点**: 调参诊断实测(20→50 改变 11/20) / `config.py` 的 `candidate_top_n` / answer 侧三闸门见 [讲解 04 篇](../rag_v01/04-生成侧全链路.md) §3.3。

**常见错误答法**: 说"20 是经验值/最佳实践"。这里有实测数字, 用数字答。

## Q7. 同父去重为什么必须放在截断之后?(深水)

**答题骨架**
因为父子分块的重叠让同一个父块下的兄弟子块在词项上高度相似, 不合并的话, top-5 里可能出现 4 条来自同一个父块 —— 模型拿到 4 遍同样的上下文, 而另外几个相关父块一个都没进来。顺序上我选**先截断、再按父块合并**: 这样"top-5" 的语义始终稳定(5 个候选子块决定的 5 个父块)。反过来先合并再截断, 就要回答"一个父块算几条"这个没有正确答案的问题。合并时是把后续命中**追加进已有条目的 hits**, 父块全文不重复拼接。

**深挖追问**
- "合并掉了会不会丢信息?" → 不丢: 命中明细(两路名次、命中文本)都在同一条的 `hits` 里, 只是父块全文只出现一次。
- "那 `rrf_rank` 是什么?" → 是父块在**最终结果**里的连续名次(1 起), 不是子块的融合槽位 —— 同父合并后槽位会跳号, 用它做名次会看到断号。
- "怎么验证的?" → 单测里有专门用例; 真机冒烟时看到 `Table of Contents` 的 4 条同父子块合并成 1 条。

**证据锚点**: `retrieve.py:123-141` / `contracts.py:111-128` 的 `RetrievedChunk` 注释 / `test_retrieve.py` 的同父合并用例。

**常见错误答法**: 说"用 `distinct` 之类去重" —— 关键是**顺序**(在截断后)与**不丢明细**(hits 累积), 不是去重动作本身。

## Q8. 线上用户问"库里有答案的问题", 却答"没找到", 你怎么查?(实战)

**答题骨架**
按链路从后往前切: 先确认**库里到底有没有** —— `cli list` 看文档、`cli search "关键词"` 直接检索, 这一步就把"数据问题"和"链路问题"分开了。如果 CLI 能检索到而 agent 答没有, 问题在适配层或子智能体(比如工具返回的 JSON 被模型忽略了、`(doc_id, seq)` 去重把不同块折成一条)。如果 CLI 也检索不到, 依次看: query 是否太长太宽(换成名词短语)、是不是专有名词(那是向量路的弱项、BM25 该救回来)、库里那份文档切出来的块是否异常(像"只有标题"的空壳块)。最后还有一类容易漏的: **环境变量没加载**(`.env` 不会被自动读), 表现为直接抛异常而不是返回空。

**深挖追问**
- "怎么区分'检索不到'和'库挂了'?" → 这是我的设计约束: `search()` 返回 `[]` **只表示库里确实没有**, 基础设施故障一律上抛 —— 否则故障会被包装成"知识库没有资料"的诚实回答, 最误导人。
- "如果检索到了但没答对?" → 看评估报告里的逐题明细(有生成回答那一列)和 `debug` 字段里的两路名次, 判断是"相关块没进 top-5"还是"进了但模型没用好"。
- "会不会是分词把关键词过滤了?" → 会。我加了 138 个停用词的 analyzer, 验收口径是"服务端分词与本地 jieba 的差集 ⊆ 停用词表"; 真怀疑的话用 `run_analyzer` 看实际的 token。

**证据锚点**: [讲解 03 篇](../rag_v01/03-检索侧全链路.md) §九排障表 / `retrieve.py:105-107`(空 vs 上抛的语义) / `embed.py` 的 injected 警告。

**常见错误答法**: 一上来就怀疑模型"幻觉"或"提示词有问题" —— 先排除数据与链路, 再谈提示词。
