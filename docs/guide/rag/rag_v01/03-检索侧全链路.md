# 03-检索侧全链路

> 一句话: 一句 query 进来, 走两条互不相干的路各取 20 个候选子块, 用名次融合成一份排序, 取 top-5 回溯成父块, 同父去重后交给上层 —— 每段都能单独解释, 也能单独排障。
> 对应实现: `src/rag_v01/retrieve.py`(编排) + `src/rag_v01/store.py`(两路检索原语) + `src/tools/rag/kb_search.py`(agent 侧适配层)
> 前置: [02-入库侧全链路](./02-入库侧全链路.md) | 下游: [04-生成侧全链路](./04-生成侧全链路.md)
> 证据: `src/rag_v01/tests/test_retrieve.py`(30 项) / `src/rag_v01/tests/test_kb_search.py`(8 项) / 真机冒烟手算 RRF 逐条相等(`1/(60+r_d)+1/(60+r_s)`)

## 一、一次检索的全貌

```text
search(query, top_k=None)
  │  ① top_k 校验(非正在花 embedding 之前就抛)
  │  ② 只有一条路: query 永远走文本路
  ├─→ dense 路:  embed_query(query) → HNSW(ef) → 取 candidate_top_n=20
  └─→ sparse 路: Milvus 内置 BM25(服务端用 analyzer 分词) → 取 candidate_top_n=20
        │
        ▼  ③ RRF(k=rrf_k=60) → 按 Σ 1/(k+rank) 排序 → 截 top_k=5
        │
        ▼  ④ 父块批量点查(parent_id in [...]) → 保留首次出现顺序
        │
        ▼  ⑤ 按父块合并: 同一父块的多个命中子块并进同一条的 hits
        │
        ▼
   list[RetrievedChunk](父块全文 + 命中明细 + source/page_no/heading_path)
```

五段各自独立可测: 两路检索是 `store.py` 的纯读写原语, 融合是纯函数, 回溯与合并是本地字典操作。**没有任何一段依赖上一段的内部结构**(融合只吃 `(chunk_id, score)` 对与名次)。

## 二、query 侧的三条规矩

1. **query 只走向量路的 embedding, 不进任何预处理**: `retrieve.py:113` 里 query 走 `embed_query`, 而稀疏路把 **query 原文直接交给 Milvus**(`store.py:443-458`)。两侧口径必须一致 —— 服务端用什么分词入库, 就用什么分词查库; 客户端自己分词再传会得到两套口径, 分数与名次都不可信。
2. **`top_k` 校验在花 embedding 之前**(`:110-112`): 非法 `top_k` 应该在花钱之前就报错, 而不是白跑一次 API 再抛异常。
3. **`search()` 的 `[]` 只表示"库里确实没有相关内容"**(`:105-107`): 基础设施故障(Milvus 连不上、embedding 报错)一律**上抛**, 不吞成空列表。这条很关键 —— 如果故障返回 `[]`, 上层会把它当成"知识库没有资料", 用户拿到的是"根据资料无法回答", 而真相是"库挂了"。测试里专门有一例断言故障不被吞掉。

## 三、dense 路

`store.dense_search(vec, limit, *, ef=None)`(`:423-440`):

- 索引是 **HNSW + COSINE**, `M=16` / `efConstruction=200`(建索引期, 硬编码在 `store.py:42-43`), `ef` 是**查询期**参数(默认 `config.hnsw_ef=96`)。
- `ef` 必须 ≥ `limit`(库要求), 且**只能通过参数传, 不在索引里** —— 所以它可以在不重建索引的前提下调整。
- 查询用 `consistency_level="Strong"`: 单用户本地库, 一致性优先于延迟, 避免"刚入库就查不到"这种反直觉现象。
- 分数取的是 `distance`(`_hit:486-501`), COSINE 下等价于相似度, 越大越相关。

**向量侧的两个精度前提**: 向量经过 L2 归一化(`embed.py:36-45`), 分数落在 [-1, 1]; 以及**入库与查询必须用同一个 embedder**(同一个模型、同一个维度、同一个后端) —— 换个模型就是另一个空间, 这一点由维度自检 + 环境变量唯一的读取点兜住。

## 四、sparse 路与 jieba 治理

### 4.1 一切都在服务端: analyzer 是 schema 级配置

`children` 集合的 `text` 字段声明了 `enable_analyzer=True` + `analyzer_params = {"tokenizer": "jieba", "filter": [stop]}`(`store.py:89-96`)。这带来两个后果:

- **入库不用管分词**: 原始文本进, 服务端生成 `sparse` 向量, 客户端 payload 不写 `sparse` 字段。
- **改词表就要重建表**: analyzer 是建表时写进 schema 的, 改它不能原地更新 —— 必须 drop 后重建并重灌语料。这是"想做分词治理"的真实成本, 也是 [08 篇](./08-调参与容量手册.md) 里"必须重灌的三类改动"之一。

### 4.2 为什么必须加停用词表

**这是这个项目里最有教学价值的一次实测**: jieba analyzer 会把**空白和标点也切成 token**。在一个 20 个子块的样例语料里共 2540 个 token, 其中空格 1109 个(**44%**)、表格竖线 331 个、换行 62 个。

为什么这很致命? 因为 **RRF 只吃名次, 不吃分数**。带空格的 query 会让这些噪声 token 命中一大批无关子块, 而它们拿到的名次与真信号子块**完全等值** —— 噪声票直接参与融合, 把真命中挤出 top-5。如果换成"分数加权融合", 噪声的高分至少还会被权重稀释; 名次融合下没有这道缓冲。

对策是给 analyzer 加 `filter`(`store.py:52-62` 的 138 个停用词), 并加第三道建表自检(`_check_analyzer`)拦住旧表。**一个附带发现**: 该 tokenizer **只支持 `stop` 这一种 filter**, 试过的 `removepunct` / `length` / `alphanumonly` / `lowercase` 全部报 `unsupport filter type` —— 所以标点治理也只能靠停用词表办。

### 4.3 停用词的验收口径

不是"看着差不多", 而是可断言的: **服务端 `run_analyzer()` 的 token 与本地 `jieba.lcut_for_search(HMM=True)` 的差集, 必须 ⊆ 停用词表**。这条口径让"分词对齐"从感觉变成了检查项。

## 五、RRF 融合

### 5.1 公式与直觉

`rrf_fuse(dense, sparse, *, k, top_k)`(`retrieve.py:40-87`), 每个候选子块的分数是:

```text
score(doc) = Σ_routes 1 / (k + rank_in_that_route)
```

`k=60` 的直觉: 名次差被压缩进分母, `k` 越大, 1/(k+1) 与 1/(k+20) 的差距越小 → 两路的**第一名与第二十名**贡献更接近, 融合更像"投票"; `k` 越小, 靠前的名次越占绝对优势。60 是文献里的常用值, 这里也**没有把它当超参去调**(调参优先级见 [08 篇](./08-调参与容量手册.md))。

### 5.2 五个实现细节(每个都对应一类 bug)

| 细节 | 位置 | 不这么做会怎样 |
|---|---|---|
| 名次**从 1 起**, 不用 0 哨兵 | `:66` | 用 0 会让第一名贡献 `1/k` 而非 `1/(k+1)`, 且与"未命中"的表示混淆 |
| 双路命中用 `setdefault` **保留先见到的那条** | `:69-71` | 后者覆盖前者会让展示字段随机漂移 |
| **同分按 `chunk_id` 兜底排序** | `:75` | 同分数值顺序不稳定 → 单测与评估回归不可复现 |
| **先排序后 `round`** | `:84` | 先 `round` 再排序会让本可区分的名次被抹平, 顺序随机 |
| `k` / `top_k` **不给默认值** | `:53-57` | 函数默认值与 `config.py` 两个默认值来源会漂移, 改一处忘一处 |

另外两条"天然退化"的设计:**单路为空时不报错**(`:53-57`), 融合自动退化成另一条路的排序; 两路都空才返回 `[]`。

### 5.3 为什么不用 Milvus 原生 `hybrid_search`

原生融合一行就能调, 但**中间量拿不到**: 每个最终结果的两路名次是评估归因的关键输入("这题没答对, 是 dense 没召回还是 sparse 没召回")。手写 RRF 的代价是自己保证 §5.2 那五条正确性, 收益是整条链路的可解释性 —— 详见 [01 篇](./01-设计构思与关键选型.md) §2.6。

## 六、父块回溯与同父去重

### 6.1 回溯: 一次批量点查

融合结果拿到的是子块 id, 但**喂给模型的是父块全文**。做法是: 从融合结果里按顺序收集 `parent_id`, 去重保序, 再一次 `parent_id in [...]` 批量点查(`store.get_parents:461-483` 返回 dict)。缺父块(数据不一致)时**跳过并告警**, 不崩。

### 6.2 同父去重: 在截断**之后**

顺序是: 先截 top_k, 再按父块合并(`:123-141`)。如果反过来(先按父合并再截断), 就得面对"一个父块算几条"这种没有正确答案的问题; 而且**截断后合并**能保证"top-5" 始终是"5 个候选子块决定的 5 个父块", 语义稳定。

合并动作是: 同一父块的后续命中**追加进已有条目的 `hits`**, 父块全文**永不重复拼接**。为什么必须合并? 父子分块的重叠区让同父兄弟子块的词项高度相似, 不合并的话 top-5 里可能出现 4 条来自同一个父块 —— 模型拿到 4 遍同样的上下文, 而另外 4 个相关父块一个都没进。

### 6.3 `rrf_rank` 的语义

`RetrievedChunk.rrf_rank` 取的是**该父块在最终结果里的连续名次**(1 起), 不是子块的融合槽位 —— 因为同父合并后槽位会跳号。这个字段最大的用途是评估报告里的"相关块排第几"。

## 七、契约: 检索侧两个类型

`contracts.py:94-128`:

| 类型 | 字段 | 说明 |
|---|---|---|
| `ChildHit` | `chunk_id` / `text` / `chunk_type` / `dense_rank` / `sparse_rank` / `rrf_score` | 挂在父块下的命中明细。两个名次 `None` 表示该路没进前 N(从 1 起, 不用 0 哨兵, 否则与"未命中"歧义) |
| `RetrievedChunk` | `parent_id` / `parent_text` / `rrf_rank` / `hits`(≥1) / `doc_id` / `source` / `page_no` / `heading_path` / `metadata` | **一个父块一条**; `parent_text` 才是最终喂模型/给人读的上下文主体 |

`hits` 恒 ≥ 1: 只有被至少一个子块命中的父块才会出现在结果里。两个名次字段进契约而不是只留在 `retrieve.py` 内部, 是因为**融合之后再也拿不到它们** —— 评估要看"某路召回强不强", 排障要看"命中来自哪一路", 都得靠这两个数。

## 八、适配层: 从 `RetrievedChunk` 到工具 JSON

`src/tools/rag/kb_search.py` 是 agent 侧唯一的检索入口, 它把内核结果转成**接收方定的** JSON 契约:

| JSON 键 | 来源 | 说明 |
|---|---|---|
| `doc_id` | `RetrievedChunk.doc_id` | 直接映射 |
| `filename` | `RetrievedChunk.source` | 直接映射(入库时的文件名) |
| `seq` | `chunk_id` 的 `:cNNN` 段(`_seq_of:45-50`) | 兼容旧的 `(doc_id, seq)` 去重键; 解析不出数字回 **0**, 不给 `None`(否则去重键错位) |
| `content` | 父块全文 + `"\n---\n"` + `hits[0].text`, 再截 500 字 | **升级点**: 旧工具只回 500 字切片, 子智能体读到的是半句话 |
| `score` | `hits[0].rrf_score` | 父块内最佳子块的融合分, **越大越相关** |

三条工程细节:

- **工具名保持 `kb_search`**: `prompts/subagents/retriever.md` 里写死了这个名字, 而提示词是静态前缀(为前缀缓存服务), 改名要动提示词并让缓存失效 —— 不值得。
- **`top_k` 钳制到 1~10**(`:61`): 防模型给异常值拖垮检索。
- **注入点在 `_default_search`**(`:34-42`): 真检索转调 `rag_v01.search`, 测试 monkeypatch 这个函数注入假检索; `from rag_v01 import search` 写在**函数体内**, 避免顶层 import 把 docling/torch 拖进 agent 进程。

> ⚠️ **已知遗留问题**: `prompts/subagents/retriever.md:10` 把 `score` 描述成"越小越相似", 与实现的"越大越相关"**方向相反**(RRF 融合分是越大越好)。这是提示词侧的文字错误, 不影响功能(模型不据此做判断), 但**讲这套系统时不要照抄这句**。已记入 [07 篇](./07-技术细节与坑位手册.md) 第 8 组与本专题 TODO。

## 九、失败语义与排障对照表

| 现象 | 可能原因 | 先查哪里 |
|---|---|---|
| 返回 `[]`, 上层答"根据资料无法回答" | 库里确实没有相关内容 | `python -m rag_v01.cli list` 看库里有没有文档; 再 `search` 试更短的名词短语 |
| 抛异常而不是空结果 | Milvus 连不上 / embedding 报错 | `store.get_client()` 连通性; `.env` 的 `RAG2_*` 是否加载(裸 `python -c` 看不到) |
| 明明库里有关键词却检索不到 | analyzer 停用词表把该词过滤了; 或表是旧 schema | `_check_analyzer` 的哨兵抽验; 必要时重建 collection |
| 命中的都是同一个父块 | 同父去重失效(改动 `retrieve.py` 后) | `RetrievedChunk.hits` 的长度与 `rrf_rank` 连续性 |
| 分数都挤在 0.03 附近分不开 | RRF 分数的正常量级(≈2/(60+1)≈0.033), 不是 bug | 看名次(两路 rank)而不是看分数绝对值 |
| 图片块命不中 | 图片向量退化成了文本向量 | `embed_chunks` 的 `dropped` 警告; `RAG2_IMAGE_DIR` 是否拼上(见 [07 篇](./07-技术细节与坑位手册.md)) |
