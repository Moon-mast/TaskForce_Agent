## 一、先看约束, 再看选型

选型是被约束推出来的, 不是"哪个先进用哪个"。这个项目的约束有四条, 每条都排除了几个看起来更高级的方案:

| 约束 | 具体表现 | 直接排除了什么 |
|---|---|---|
| **单用户、本地跑** | 一台 Windows 开发机, WSL 里的 docker 起 Milvus, 没有集群 | 需要 K8s/分布式部署的方案; 需要多租户隔离的设计 |
| **面向实习求职 + 学习** | 技术决策要能讲清楚"为什么", 而不是"框架帮我都做好了" | 全托管服务(黑盒)、把关键路径藏在框架里的做法 |
| **语料规模小** | 个人文档几十到几千份, 不是百万级 | 需要大规模分片/离线索引流水线的方案 |
| **成本敏感** | 每次评估都是真金白银的 LLM 调用 | 无上限的重排器、多轮 query 改写、每题多路并跑 |

由此得到目标: **一条能跑通、能解释、能量化、能替换的本地知识库链路**。下面六个选择都服务于这四条。

## 二、六个关键选型

### 2.1 解析: docling 统一三格式, 而不是手拼三件套

| 候选 | 说明 | 结论 |
|---|---|---|
| **docling** | 一套 API 处理 pdf/docx/md, 输出统一文档对象(带阅读顺序、页码、表格结构、图片) | **选中** |
| pypdf + python-docx + 手写 md | 旧 `tools/rag/parse.py` 的做法 | 否决 |
| unstructured | 也能统一多格式 | 否决 |

**选它的理由**: 我们要的不只是"文字", 而是**结构** —— 标题层级(决定父块边界)、页码(决定引用可追溯)、表格(决定是否原子切分)。手拼三件套拿不到这几样: pypdf 只给纯文本流, 表格会被拍平成一行字。实测细节(docling 2.128 的 `TitleItem` 无 `level`、`prov` 顺序、`content_layer` 语义)见 [02 篇](./02-入库侧全链路.md) §二。

**代价**: 首次解析 pdf 会下载约 506MB 的版面/表格模型; md 与 docx 两个后端能力不一致(比如 md 的图片永远取不到本体, 见 [07 篇](./07-技术细节与坑位手册.md))。这两条都写进了文档而不是"事后才发现"。

### 2.2 分块: 父子分块(small-to-big), 而不是定长切

| 候选 | 说明 | 结论 |
|---|---|---|
| **父子分块** | 父块沿标题层级聚合(1200~1800 字), 子块在父块内递归切(450 字/重叠 50); **检索用子块, 喂模型用父块** | **选中** |
| 定长切分 | 旧系统的 500 字 / 重叠 100 | 否决 |
| 语义分块(embedding 相似度断点) | 用向量距离决定边界 | 否决 |

**选它的理由**: 检索要"窄", 生成要"宽"。子块小, 向量更聚焦, 命中率更高; 但只把 450 字喂给模型, 它拿到的是**半句话**。父子分块把这两件事分开: 用子块找, 用父块答。旧系统是"500 字切片直接喂模型", 这正是新旧对比里精度提升的一大来源(见 §四)。

**否决语义分块的现实理由**: 它引入一个新的 embedding 依赖(要额外跑一遍向量)与一个新的超参(阈值), 在这个语料规模上的收益无法验证 —— "无法验证的复杂度不加" 是这个项目的一条隐性纪律。

### 2.3 向量库: Milvus standalone, 而不是 pgvector / Chroma / FAISS

| 候选 | 说明 | 结论 |
|---|---|---|
| **Milvus 2.6 standalone** | WSL docker, 19530 端口; 内置 BM25 Function + HNSW + 稀疏倒排, 一个库同时提供两路检索 | **选中** |
| pgvector | 旧系统用的, 复用 PostgreSQL 5433 | 否决(见下) |
| Chroma / FAISS | 轻量、纯本地文件 | 否决 |

**选它的理由**: 关键在**稀疏路**。Milvus 2.6 内置了 BM25 Function 与 jieba analyzer —— 入库存文本, 服务端自动生成稀疏向量并建倒排索引, 检索时把 query 原样交给服务端分词。换成 pgvector 就要在客户端自己维护一份 BM25 索引(旧系统就是这么做的: `rank_bm25` 内存索引 + 脏标记重建), 多一份状态、多一处不一致风险。FAISS/Chroma 没有稀疏路, 只能自己再搭一套。

**否决**的另外两条现实理由: pgvector 的向量能力上限低(HNSW 参数不可调、混合检索要手写 SQL), 而 Chroma 在 Windows 上的稳定性与 Milvus 在 docker 里的可复现性相比不占优。

**代价**: 多一个 docker 依赖(WSL 里三个容器: etcd/minio/milvus), 开发机要能起容器; 以及 **Milvus 的几条硬约束**(collection 必须有向量字段、每个向量字段必须有索引、向量字段不支持 nullable、维度下限 2) —— 这些约束逼出了 `parents` 集合的"占位零向量"设计, 见 [07 篇](./07-技术细节与坑位手册.md) 第 1 组。

### 2.4 稀疏检索: 服务端内置 BM25, 而不是客户端 rank_bm25

已并入 §2.3 的讨论, 单独列一条是因为它有过一次**真实的踩坑**: jieba analyzer 会把空白与标点也切成 token(实测样例 20 个子块共 2540 个 token, 其中空格 1109 个 = 44%)。RRF 只吃名次, 于是"噪声票"与"真信号票"等值, 融合结果被空格污染。对策是给 analyzer 配 stop 停用词表 + 建表自检, 见 [03 篇](./03-检索侧全链路.md) §四与 [07 篇](./07-技术细节与坑位手册.md) 第 2 组。

**这条坑的通用教训**: 分数加权融合里"假高分"会被稀释, 名次融合里"假名次"是致命的 —— 融合方式决定了你要防什么。

### 2.5 嵌入: 百炼多模态 API, 而不是本地 bge-m3

| 候选 | 说明 | 结论 |
|---|---|---|
| **百炼 `qwen3-vl-embedding`** | DashScope SDK, 文本与图片**同一向量空间**, 维度 1024 | **选中**(默认) |
| 本地 bge-m3 | 纯文本, 离线, 不花钱 | 保留为备选(`rag2-local` extra) |
| 纯文本 API(`qwen3.7-text-embedding-flash`) | 更便宜, 但图片只能退化处理 | 备选(语料全是文本时可用) |

**选它的理由**: 解析阶段会把 pdf 里的插图单独落盘, 如果 embedder 只能处理文本, 这些图片块就只能拿占位文本去算向量 —— 等于**图片白提取了**。多模态嵌入让图片块进 dense 路时有真向量, 实测"图片与相关文本"的余弦相似度 0.7444, 远高于与无关文本的 0.2282, 坐实同空间。

**代价**: 依赖外部 API(要 key、有单请求上限: 文本 20 条/图片 5 条)、图片要转 data URI 上传(单图 ≤10MB), 以及一个**静默失效的坑**: 维度参数必须走顶层 `dimension=1024`, 写进 `parameters={...}` 会被忽略并返回默认的 2560 维 —— 这是 [07 篇](./07-技术细节与坑位手册.md) 第 3 组的第一条。

### 2.6 融合: 客户端手写 RRF, 而不是 Milvus 原生 hybrid_search

| 候选 | 说明 | 结论 |
|---|---|---|
| **客户端手写 RRF** | 两路各取 20 → 按 `Σ 1/(k+rank)` 融合 → 取 top-5 | **选中** |
| Milvus 原生 `hybrid_search` + `RRFRanker` | 一行调用, 服务端完成融合 | 否决(但保留为对照) |
| 分数加权线性融合 | `α·向量分 + β·BM25分` | 否决 |

**选它的理由**: 两条路的分数量纲不可比(余弦相似度 vs BM25 分), 想加权就得先归一化, 而归一化本身又依赖分布 —— RRF 用**名次**绕开了这个问题。更关键的是可解释性: 手写之后, 每个最终结果的"两路名次"都能拿到(`ChildHit.dense_rank` / `sparse_rank`), 评估时能回答"这题没答对, 是 dense 没召回还是 sparse 没召回"; 用原生 fusion, 这些中间量拿不到。

**代价**: 自己实现就要自己保证正确性 —— 名次从 1 起、同分按 `chunk_id` 兜底、先排序后 `round`(否则结果不可复现)。这些都在 [03 篇](./03-检索侧全链路.md) §五与 [07 篇](./07-技术细节与坑位手册.md) 第 6 组里逐条写了。

## 三、四条硬原则(以及它们的代价)

| 原则 | 具体做法 | 代价 |
|---|---|---|
| **零项目依赖** | 内核不 import `agent/`、`tools/`、`settings/`; 配置自己读 `RAG2_` 环境变量, 不碰 `.env` | 入口必须负责载入 `.env`(`uv run --env-file .env` 或 `settings/config.py`), 裸 `python -c` 看不到变量 |
| **全同步** | 不用 async/await; 唯一例外是 ragas 嵌入基类强制要求的那对 `async` 薄壳(内部只是 `to_thread`) | 并发上限靠线程池; 与"高并发服务"的直觉不符, 但对单用户本地场景是对的 |
| **facade 收敛** | 对外只承诺 3 个函数 + 4 个类型; 内部模块随便重构 | 调用方要用的中间量(比如两路名次)必须显式进契约, 否则拿不到 |
| **内容寻址** | `doc_id = sha256(文件字节)[:16]` | 同一文件重复入库得到同一个 id(天然的幂等与去重), 但**没有"上传时间"概念**, 且文件改一个字节就变成新文档(要靠 `purge_stale` 清旧版本) |

第 3、4 条各自的"看不见的收益": facade 收敛让内核能整目录搬走(移植时只改入口, 见 [rag_0.1/07 篇](../../../new_module/rag_0.1/07-接口设计与移植方案.md)); 内容寻址让"重复上传"这件事不需要额外去重逻辑(`created: false` 就是它白送的, 见 [dev/front/docs/API-CONTRACT.md](../../../../dev/front/docs/API-CONTRACT.md) §2.3)。

## 四、为什么是"重建"而不是"改造旧系统"

旧系统(`tools/rag/`, 已下线)也能检索, 但它的技术栈与目标不匹配:

| 维度 | 旧系统 | 新内核 | 换的理由 |
|---|---|---|---|
| 解析 | pypdf + python-docx 手拼 | docling 统一结构 | 拿不到标题层级与页码 → 无法做父子分块与引用追溯 |
| 分块 | 定长 500/重叠 100 | 父子分块 1200~1800 / 450/50 | 检索粒度与生成粒度解耦 |
| 存储 | pgvector 单表 | Milvus 双 collection | 稀疏路下推到服务端 |
| 稀疏路 | 客户端 `rank_bm25` 内存索引 | 内置 BM25 + analyzer | 少一份需要重建的状态 |
| 嵌入 | 智谱纯文本 | 百炼多模态 | 图片块有真向量 |
| 评估 | 无 | ragas 四指标 + 新旧双跑 | 从"感觉变好了"到"能量化" |

**而且改造有一个硬障碍**: 两套嵌入模型不同(智谱 vs 百炼多模态), 向量不可比, 所以**不存在"平滑迁移"** —— 语料必须重灌。既然要重灌, 那就把整条链子一起换成目标形态。

**新旧双跑对比(40 题同语料同生成器同 judge)**:

| 指标 | 旧 `tools_rag_v1` | 新 `rag_v01` | Δ |
|---|---|---|---|
| context_precision | 0.6896 | **0.8958** | **+0.2062** |
| context_recall | 0.9000 | **0.9500** | +0.0500 |
| faithfulness | 0.8681 | **0.9595** | +0.0914 |
| answer_relevancy | 0.4774 | **0.5015** | +0.0241 |
| NaN 题数 | 9/40 | 7/40 | — |

**判读纪律**(重要, 别把这张表读成"全面碾压"): 上一轮复现性实测给出的噪声带是 —— 输入固定时 judge 自身抖动 faithfulness Δ0.20 / answer_relevancy Δ0.09, 检索侧 Δ≤0.003。所以上表里**只有上下文精度那一项明确超出噪声带**; 其余三项方向为正但落在噪声内, 不足以单独下结论。完整对照组与结论见 [05 篇](./05-质量检验策略与方法.md) §五。

## 五、被否决的备选, 什么条件下会回来

选型不是永久判决。写下触发条件, 以后就不用重新争论:

| 备选 | 触发条件 |
|---|---|
| 本地 bge-m3(纯文本离线) | 语料全为文本, 或需要断网可跑 / 有数据出域限制 |
| pgvector(复用 PostgreSQL) | 不想多起 docker 容器, 且能接受客户端自维护 BM25 |
| 语义分块 | 语料从"结构化文档"变成"长对话/访谈记录"这类无标题层级的内容 |
| 重排器(rerank) | 候选深度调到头仍不够, 且评估显示"相关块进了 top-20 但没进 top-5" |
| 原生 `hybrid_search` | 不再需要两路名次做归因时(用可解释性换一行代码) |
| 查询改写 | 评估里"检索侧召回为 0"的题明显多于"召回但没答对"的题 |
