## 一、四层证据金字塔

```text
                ┌──────────────────────────────┐
   ④ 效果层      │ ragas 四指标 + 新旧双跑对比  │  ← 证明"变好了", 但带噪声带
                ├──────────────────────────────┤
   ③ 环境层      │ 真机冒烟清单(Milvus/embed/   │  ← 证明"在真环境里能跑"
                │ judge/重启持久性)            │
                ├──────────────────────────────┤
   ② 集成层      │ fake 集成(patch 边界 +       │  ← 证明"段落之间拼装正确"
                │ 假 Milvus 客户端)            │
                ├──────────────────────────────┤
   ① 逻辑层      │ 纯函数单测(切分/RRF/清洗)    │  ← 证明"算法本身对", 最快最稳
                └──────────────────────────────┘
```

| 层 | 覆盖什么 | **不能**证明什么 |
|---|---|---|
| ① 纯函数单测 | 清洗五规则、父子切分边界、RRF 排序与去重、`_seq_of` 等纯逻辑 | 真实文档形态下的效果; 库/服务端行为 |
| ② fake 集成 | 流水线编排顺序、字段拼装、失败隔离、契约字段完整性 | 真 Milvus 的索引与 analyzer 行为、真 API 的返回 |
| ③ 真机冒烟 | Milvus 建表/索引/分词对齐/跨模态相似度、embedding 维度、judge 可用性、重启后重连 | 检索质量好坏(只证明"能用") |
| ④ ragas + 双跑 | 检索质量与生成质量的量化对比, 在固定语料与固定测试集上 | **小差异的因果**(噪声带内不下结论); 未被语料覆盖的能力 |

**这张金字塔的用法**: 报告结论时先说清是哪一层的证据。比如"父子分块有效"是①+③层的证据(单测 21 项 + 真 pdf 人工核对), **不是**④层的 —— 因为评估语料没有多子块文档(见 §四)。

## 二、第①层: 纯函数单测

对象是"改了就能立刻知道对错"的逻辑, 不碰任何外部依赖:

| 文件 | 覆盖 | 关键用例(值得记的) |
|---|---|---|
| `test_clean.py`(12) | 五条清洗规则各一例 | 规则顺序: 先剔除再合并(顺序换了两条都会红) |
| `test_chunk.py`(21) | 父块聚合 / 子块切分 / 重叠 / 原子块 / 空壳标题 | 标题前缀只贴第一条; 子块页码按加重叠前的起点回查; 表格与图片块不切 |

这一层的价值在于**回归速度**: 21 项切分单测跑完 1 秒内, 而真机验证一次要连 Milvus + 花 API 钱。

## 三、第②层: fake 集成

`test_pipeline.py`(13 项)把 `parse / clean / split / embed / store` 全部 patch 掉, 只验证**编排**: 调用顺序、失败隔离进 `failed`、warning 合并、`purge_stale` 在 upsert 之前。`test_store.py`/`test_embed.py` 换 FakeClient / FakeBackend, 但断言的是**真 schema 对象**(pymilvus 真实构造的字段类型、索引参数、analyzer 配置), 所以"字段类型写错""索引参数写错"这类问题在这一层就能抓到。`test_cli.py`/`test_api.py` 用 monkeypatch 假件覆盖入口层的参数解析与错误分支。

这一层不连接任何真实服务, 所以能在 CI 或没起 docker 的机器上跑 —— 这是"主线不阻塞在外部依赖上"的具体做法。

### 4.1 真 pdf 的另一个收获: "父块达标率是文档形态的函数"

用真实 pdf 量父块长度分布: 37 个父块, 中位 **84 字**, 落在 1200~1800 达标区间的只有 **1/37**。这不是 bug —— 那份讲义是"多小节、每节几行"的形态, 节短就必然产出小父块。

**这条结论的通用价值**: 长度达标率是**文档形态的函数**, 不是切分器好坏的指标。所以它只用来发现异常(比如全语料 0% 达标才说明配置错了), 不当作验收门槛。

## 五、第④层: ragas 四指标与判读纪律

### 5.1 四指标各自考核哪一段

| 指标 | 考核对象 | 大致算法 | 高分意味着 |
|---|---|---|---|
| `context_precision` | **检索** | 逐条判断检索回来的上下文是否与参考答案相关, 算相关比例 | 回来的材料里没多少废料 |
| `context_recall` | **检索** | 参考答案的要点能否在检索上下文里找到 | 该找的都找到了 |
| `faithfulness` | **生成** | 回答里的每个论断是否都能被上下文支持 | 没编造 |
| `answer_relevancy` | **生成** | 由回答反推问题, 看与真实问题是否一致(judge 生成 3 个反向问题, 实测常只返 1 个) | 回答确实在回答这个问题 |

前两个变了 → 检索的问题; 后两个变了 → 生成或 judge 的问题。这个映射是归因的第一步。另有 `debug` 字段记录每题命中的两路名次, 用于回答"是 dense 没召回还是 sparse 没召回"。

### 5.2 噪声带: 这个项目最重要的一条方法学结论

**实测**(同一份中间产物、固定输入、只跑评估两遍):

| 侧 | 指标 | 两轮差异 |
|---|---|---|
| 检索侧 | context_precision / recall | **Δ = 0** |
| 判分侧 | faithfulness | **Δ = 0.20** |
| 判分侧 | answer_relevancy | **Δ = 0.09** |

**全量 40 题两轮**(生成也重跑):

| 指标 | 轮次一 | 轮次二 | Δ |
|---|---|---|---|
| context_precision | 0.8958 | 0.8932 | 0.0026 |
| context_recall | 0.9500 | 0.9500 | 0.0000 |
| faithfulness | 0.9595 | 0.9118 | 0.0477 |
| answer_relevancy | 0.5015 | 0.4735 | 0.0280 |
| NaN 题数 | 7 | 10 | — |

结论: **噪声来自 LLM 两端(生成 + 判分), 不来自检索**。于是定下判读纪律:

- **差异小于 ~0.1 不下结论**(0.09~0.20 是噪声量级)。
- 要比"参数改动的效果", 用「仅评估」入口固定同一份中间产物, 或按 (question, contexts) 缓存生成结果 —— 否则你比的是两次 LLM 抽签。
- 报告里必须写 NaN 题数: NaN 是"judge 没给出判断", 不是 0 分; 均值会忽略 NaN, 所以 NaN 多的那一轮天然"看起来更好"。

### 5.3 新旧双跑(40 题同集)

| 指标 | 旧 `tools_rag_v1` | 新 `rag_v01` | 新(重跑) | Δ(新基线 − 旧) | 是否超出噪声带 |
|---|---|---|---|---|---|
| context_precision | 0.6896 | **0.8958** | 0.8932 | **+0.2062** | ✅ 是 |
| context_recall | 0.9000 | **0.9500** | 0.9500 | +0.0500 | ❌ 否 |
| faithfulness | 0.8681 | **0.9595** | 0.9118 | +0.0914 | ❌ 否(临界) |
| answer_relevancy | 0.4774 | **0.5015** | 0.4735 | +0.0241 | ❌ 否 |
| NaN 题数 | 9/40 | 7/40 | 10/40 | — | — |

**对照条件**(不写清这些, 对比就不成立): 同一份语料(旧侧入库 500/500 篇零失败)、同一套 40 题、**同一个最简生成器**(固定 prompt + `temperature=0`)、**同一个 judge**(`deepseek-flash`); 两侧都不经本包的检索链路, 只经中间产物 jsonl 交换。唯一的差别是检索内核与它原生的上下文口径(旧侧 500 字切片, 新侧父块)。

**能下的结论**: 新内核在"喂给模型的上下文里有多少是相关的"这一项上有实质提升(约 +0.20)。其余三项方向为正但落在噪声带内, **不足以单独下结论**。

### 5.4 一次报告事故: 费用统计把整跑带崩

第一次全量评估跑到最后崩在 `total_cost()` —— ragas 的 `total_tokens` / `total_cost` 是**方法**, 且没配 token 用量解析器时会抛异常。花了半小时与真金白银的一次评估, 报告却落不了盘。对策: 统计量读取全部走容错的 `_value_of`(取不到就写 `<不可用: …>` 而不是崩)。**教训**: 报告生成路径上的每个字段都要假设"它可能抛错", 因为报告是评估的**唯一产物**。细节见 [06 篇](./06-评估工程实现.md) §五。

另一次事故: judge 账户余额不足, 39/40 题 NaN —— 报告看起来"尽力跑完了", 实际几乎全废。所以 NaN 名单必须进报告 meta, 一眼能看出"这轮不作数"。

## 六、测试集: 怎么构造的、有什么盲区

**来源**: DuReader-Robust 公开镜像(学术研究许可), 从 14,520 段里抽 500 段当语料 + 40 条当测试题。每条题自带参考答案与 `answer_start` 偏移, 所以"参考答案确实在源段落里"是**自动校验**的 —— 省掉"自己出题 + 人工校对"一整道工序。

**盲区(必须写在报告旁边)**:

| 盲区 | 后果 | 靠什么补 |
|---|---|---|
| 一段一文件、段落中位 215 字 → **1 文档 = 1 父块** | 父子分块的"多子块 / 跨页 / 同父去重"能力**未被评估覆盖** | 单测 21 项 + 真 pdf 人工核对(③层) |
| 参考答案是短语(如"300"、"周朝") | context_recall 读数偏乐观(要点少, 好命中) | 判读时按"同一份测试集内的相对变化"看, 不跨数据集比绝对值 |
| 语料是资讯问答, 不是技术文档 | 长文层级结构的检索表现没被覆盖 | 真 pdf 样板(15 页讲义)做补充验证 |

## 七、证据 → 结论映射表(引用时照着抄)

| 想说的结论 | 必须引用的证据 | 不能说什么 |
|---|---|---|
| 检索链路实现了 RRF 融合且正确 | `test_retrieve.py` 30 项 + 真机手算逐条相等 | 不能说"RRF 是最优融合方式"(只做了与旧系统的对比) |
| 父子分块有效 | 单测 21 项 + 真 pdf 156 条目页码全覆盖 | 不能说"评估证明父子分块提升了召回"(语料没覆盖) |
| 换内核让检索质量提升 | 双跑 40 题, 精度 +0.206 | 不能说"四项全面碾压"(只有精度超噪声带) |
| 评估结果可复现 | 检索侧 Δ≤0.003; 生成侧 Δ≤0.048(附噪声带说明) | 不能说"完全可复现"(生成侧不可复现) |
| 系统能跑、能重启、不丢数据 | ③层冒烟清单(含重启持久性) | 不能据此说"生产可用"(单用户本地场景) |
| 全链路没坏 | 全套件 402 passed / 2 failed(沙箱外部依赖) | 不能忽略那 2 条失败不提 |
