# 08-调参与容量手册

> 一句话: 想改质量先别看 `ef` —— 实测它对结果**不敏感**; 真正动得了结果的是候选深度与分块尺寸, 而改分块尺寸或维度**必须重灌语料**。
> 对应实现: `src/rag_v01/config.py`(可调项) + `src/rag_v01/store.py`(硬编码项与容量相关常量)
> 前置: [03-检索侧](./03-检索侧全链路.md) / [05-质量检验策略与方法](./05-质量检验策略与方法.md) | 下游: 无(本篇是手册的收尾)
> 证据: 调参诊断实测(ef 三档 20/20 一致; 候选深度 20→50 改变 11/20 条 top-5)、`eval_reports/` 四份报告的 meta 参数快照

## 一、旋钮总表

### 1.1 可调(`config.py`, 环境变量 `RAG2_` + 字段名大写)

| 旋钮 | 默认 | 影响面 | 怎么测 | 优先级 |
|---|---|---|---|---|
| `candidate_top_n` | 20 | 每一路进融合的候选数 → 直接决定 top-5 的构成 | 固定中间产物跑「仅评估」对比 precision/recall | ★★★ |
| `retrieve_top_k` | 5 | 喂给模型的父块数 → 上下文量与生成质量 | 同上; 注意 answer 侧另有 4 条/1200 字的截断闸门 | ★★★ |
| `parent_target_chars` | 1500(区间 1200~1800) | 生成侧上下文粒度 + BM25 命中粒度 | 改后**必须重灌**; 用真 pdf 看块长分布 | ★★★ |
| `child_target_chars` | 450 | 召回粒度与同父合并效果 | 改后**必须重灌**; 固定 20 题对比 | ★★ |
| `child_overlap_chars` | 50 | 同父兄弟子块的词项重叠度 | 改后**必须重灌**; 单测已锁 40~50 区间 | ★★ |
| `hnsw_ef` | 96 | 查询期搜索宽度(召回率 vs 延迟) | 直接改环境变量重跑检索即可 | ★(实测不敏感) |
| `rrf_k` | 60 | 名次差的压缩程度 | 只有 `k` 很小时才明显; 没做过调参 | ☆(默认值来自文献口径) |
| `embed_dim` | 1024 | 向量表达能力 vs 存储/成本 | 改后**必须重建表并重灌** | ☆(别动) |
| `embed_batch` / `embed_img_batch` | 20 / 5 | API 单请求条数(百炼上限) | 只在报限流错误时下调 | ☆(别动) |
| `short_line_max` | 30 | 清洗规则 5 的合并阈值 | 改后重灌才生效 | ☆ |
| `do_ocr` | false | 扫描件才开(开了文本型 pdf 只会更慢) | 看清洗警告里 U+FFFD 占比 >1% 才考虑 | 按需 |
| `image_desc` | off | 图片描述增强(需 VLM 配置) | 本期未实现, 留开关位 | — |
| `milvus_uri` | localhost:19530 | 连哪个库 | — | — |

## 二、调参顺序: 先动什么、后动什么

```text
① 先固定评测条件(否则你测的是 LLM 抽签)
      └─ 用「仅评估」入口固定同一份中间产物, 或按 (question, contexts) 缓存生成结果
② 再动候选深度 candidate_top_n  ── 只影响检索, 不必重灌, 见效最直接
③ 再动 retrieve_top_k            ── 但要同步看 answer 侧的三闸门有没有把多出来的吃掉
④ 分块尺寸(parent/child)        ── 必须重灌, 影响面最大, 放最后动
⑤ ef / rrf_k                     ── 实测收益小, 除非有明确证据(比如召回率随 ef 上升)
```

**为什么这个顺序**: 越靠前的改动**代价越小、可回滚**。改 `candidate_top_n` 只写一个环境变量就能重跑; 改分块尺寸要重建 collection 并重灌 500 篇(约 2 分钟 + API 费用)并让此前所有报告失去可比性。

## 三、实测结论(这些数字比直觉有用)

| 实验 | 结果 | 结论 |
|---|---|---|
| `hnsw_ef` = 64 / 96 / 128 | 20 题里 **20/20 结果一致** | **ef 在这个数据规模上不敏感**, 别在它上面花时间 |
| `candidate_top_n` = 20 → 50 | 20 题里 **11/20** 的 top-5 结果发生变化 | 候选深度**才是**动得了结果的旋钮 |
| 同一份中间产物评两遍 | 检索侧 Δ=0, 判分侧 Δ0.09~0.20 | 没有固定输入时, 小改动根本测不出来(见 [05 篇](./05-质量检验策略与方法.md) §5.2) |
| 全量 40 题重跑 | 检索侧 Δ≤0.003, 生成侧 Δ≤0.048 | 检索侧可复现, 生成/判分侧不可复现 |

**为什么 `ef` 不敏感**: 语料只有几百个子块, HNSW 的图很小, `ef=64` 已经足够搜到真正的近邻 —— 搜索宽度是给"百万级向量、图很深"的场景准备的手段。这也解释了为什么不该照搬网上的调参经验: **要按自己的数据规模判断哪个旋钮有意义**。

## 四、必须重建/重灌的三类改动(最容易漏的运维后果)

| 改动 | 后果 | 为什么 |
|---|---|---|
| `embed_dim` 改变 | **必须重建两个 collection + 重灌全部语料** | 表结构里的向量维度写死了; 换维度就是换空间, 旧向量不可用 |
| `_ANALYZER_STOP_WORDS`(或任何 analyzer 配置)改变 | **必须重建 collection + 重灌** | analyzer 是建表时写进 schema 的, 不能原地更新 |
| `parent_target_chars` / `child_target_chars` / `child_overlap_chars` / `clean.py` 规则改变 | **必须重灌**(表结构不用改) | 块是入库时算好的, 检索期不会再切 |

**不用重灌的改动**: `candidate_top_n` / `retrieve_top_k` / `rrf_k` / `hnsw_ef`(纯查询期参数)、`kb_search` 的截断与钳制、agent 侧提示词与预算。**判断依据很简单**: 这个参数影响的是"数据长什么样"还是"怎么查数据"。

`purge_stale` 让"重灌"变得安全: 同源文件重灌会自动清掉旧 doc_id 的版本([02 篇](./02-入库侧全链路.md) §6.3), 不会留下新旧两份。

## 五、容量与性能

### 5.1 实测数据

| 项 | 实测 | 备注 |
|---|---|---|
| 入库 500 篇语料 | **1m59s** | 含解析 + 清洗 + 切分 + 嵌入(API) + 落库; 约 4 篇/秒 |
| 单篇真 pdf(15 页) | 首次 72.76s(含下载 506MB 模型) → 之后 **11s** | 模型是进程级缓存 |
| 40 题全量评估 | 约 **32 分钟** | 瓶颈是 LLM 生成 + 判分, 不是检索 |
| 检索延迟 | 亚秒级(本地 Milvus + 一次 embedding API) | 主要耗时是 query 的 embedding 往返 |

### 5.2 存储

当前库(499 文档): `children` 597 行 + `parents` 499 行。单行成本的大头是 `dense` 向量: **1024 维 float32 ≈ 4KB/行**, 所以 10 万子块 ≈ 400MB 向量数据(还不算索引)。父块的占位向量只有 8 字节, 可忽略。

### 5.3 几个"看着慢其实没问题"的点

| 现象 | 说明 |
|---|---|
| `list` 子命令慢 | `list_docs` 把 children 全量拉回客户端聚合(Milvus 无 `GROUP BY`); 定位是**运维动作**, 不是检索热点 |
| 入库过程中查不到刚写的 | `flush` 整批只调一次([02 篇](./02-入库侧全链路.md) §6.4) |
| 删完立刻查不到, 但磁盘没释放 | 删除是逻辑删除 + 时间戳过滤, 物理回收等 Milvus 自己 compaction |
| 检索分数都挤在 0.03 附近 | RRF 分数量级正常(≈2/(60+1)), 别当成"分数很低" |

## 六、怎么测才可信(实验方法)

这套系统里"改一个参数看看效果"很容易自欺。四条纪律:

1. **固定输入**: 用 `--samples <既有中间产物>` 只评不检索, 或缓存生成结果 —— 否则两次跑的是两次 LLM 抽签。
2. **一次只动一个旋钮**: 尤其是分块尺寸与候选深度**同时**动, 你没法归因。
3. **先小样本试跑**: `--limit 5` 看账单与是否崩, 再放全量。
4. **差异小于 0.1 不下结论**: 判分侧噪声就是这么宽; 想知道"是否真的变了", 看**逐题**而不是看均值 —— 11/20 条 top-5 变化这种"逐题级差异"比均值差 0.01 有说服力得多。
