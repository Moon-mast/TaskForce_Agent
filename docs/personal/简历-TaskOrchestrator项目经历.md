## 一、应用定位

**一句话定位**：把「研报库 + 公告舆情 + 估值计算」三条证据链串起来，为单只标的产出一份**每条结论都可溯源**的一页纸研究报告。

| | |
|---|---|
| **目标用户** | 独立投资者 / 小型私募研究员（单用户 + 本地部署，与项目定位吻合） |
| **核心痛点** | 做一只票的研究，要在三处来回切：翻自己攒的研报 PDF、查最新公告与可比公司动态、开 Excel/Python 算估值与回测。单次 2–3 小时，且**做完之后说不清哪条结论来自哪里** |
| **交付物** | 一页纸决策报告 = 结论 + 依据 + 来源标注（本地库 / 外部检索 / 实跑结果） |

### 与「又一个荐股 Bot」的区别（面试必答）

本项目**不给买卖建议、不预测涨跌、不接实盘**，只做**信息聚合 + 计算 + 溯源**。这样定位有两个好处：

1. 避开荐股合规风险，同时体现产品与合规意识；
2. 把技术亮点让给架构本身——面试官不会被「你这策略能赚钱吗」带偏，而是聚焦多智能体编排。

## 二、专业技能（直接复制）

- **Agent 与大模型应用**：熟练 **LangGraph**（supervisor 结构化路由、`Send` fan-out 并行派发、`interrupt` 单点 HITL、checkpointer/Store 双层状态、子图私有上下文隔离）、LangChain；**Multi-Agent 架构**设计；**Prompt 工程**（模板外置、`$name` 占位符渲染、KV cache 前缀优化）；**MCP 协议**接入（stdio / streamable-http 双传输）
- **RAG 与检索**：**Docling** 文档解析（PDF/Word 版面还原、表格抽取、图片导出）；父子分块（子块检索 / 父块喂模型）；**Milvus** 内置 **BM25**（jieba 分词）+ 多模态向量双路召回、**RRF** 排名融合；**RAGAS** 四指标评估（精度 / 召回 / 忠实度 / 相关度）
- **后端工程**：**Python**（主力）、**FastAPI**、PostgreSQL、SQL、Git；RESTful 设计与 SSE 流式接口
- **存储与基础设施**：**PostgreSQL / pgvector**（记忆与状态）、**Milvus**（向量库 + 稀疏倒排，Docker 部署）、PostgresSaver / PostgresStore 持久化；Docker 与 Docker Compose；远程沙箱（执行面隔离）
- **工程实践**：pytest 单元与契约测试、ruff 静态检查；Vue 3 + TypeScript（独立完成 Web 工作台）；AI 辅助开发（Claude Code / OpenCode / Zcode）

### 技能栏三条硬规则

1. **没证据的别写**：每项都是给面试官**提问用的导航**。原稿的 `CI/CD` 已删——写了就可能被问「pipeline 怎么配、灰度怎么做」；Docker Compose + pytest + ruff 已足够支撑「工程规范」的印象。
2. **与项目经历互相印证**：

| 技能栏写的 | 项目里的证据 |
|---|---|
| LangGraph 多智能体 | supervisor + 3 子图 + `Send` fan-out |
| 双层记忆 | PostgresSaver + PostgresStore + pgvector |
| 混合检索 | Docling 解析 + 父子分块 + Milvus(内置 BM25 + 向量) + RRF |
| HITL | `interrupt()` 单点挂起 |
| Docker / Compose | 本地 PG + pgvector 容器; Milvus(etcd/minio/milvus)容器 |
| Vue + TS | Web 工作台（CLI / FastAPI / Web 三入口） |

3. **Docling 只出现一次**（原稿在「后端工程」与「RAG」重复），归 RAG 行——它本就是文档解析/入库环节的工具。

### 「AI 辅助开发」措辞说明

原稿写「Vibe Coding 工作流」，已改为「AI 辅助开发」。原因：中厂以上面试官看到 "Vibe Coding" 容易解读为「靠 AI 生成、缺少工程判断」；而实际用的是**规范驱动的 AI 辅助开发**（契约先定稿、模块按编号推进、测试与业务分工），措辞不必自我贬低。

## 三、项目经历 · 定稿（5 条，直接复制）

**基于 LangGraph 的多智能体投资研究助手**　｜　个人项目 · 独立完成　｜　【补时间区间】
技术栈：Python · FastAPI · LangGraph · PostgreSQL/pgvector · Milvus · SSE · pytest

- **多智能体并行编排**：针对单 Agent 串行处理检索/调研/计算致上下文膨胀、单标的研究 2–3 小时，supervisor 结构化路由将任务经 Send 以自包含契约派发线程池并行，派发不阻塞对话；配轮数上限与失败摘要兜底。
- **智能体通信协议**：针对子图共享对话历史致 token 与噪声膨胀、各自定义输入输出致改动传导，采用单向结构化通信：下行只发 TaskContract 四件套、上行只回定长 ResultSummary，两端过 Pydantic 校验，子图可独立替换。
- **双层记忆架构**：针对跨天追问时会话已丢失，短期按 thread_id 由 Postgres checkpointer 持久化、断线可续聊，长期将持仓与估值假设压缩为原子事实存入 PostgresStore，pgvector 语义检索 + 工具按需调用。
- **混合检索 RAG**：针对研报篇幅长，单一扁平化切片易切散结论与依据、关键词与语义漏召回，改为 docling 结构化解析 + 父子分块（子块检索、父块喂模型）+ Milvus 内置 BM25 与多模态向量双路召回、RRF 名次融合；用 RAGAS 四指标建基线并做新旧双跑：同语料同测试集下上下文精度 **0.69 → 0.90**、召回 0.90 → 0.95（40 题，同一 judge）。
- **人机协同与工程化**：针对子图各自追问会产生多个挂起点，interrupt() 仅在主图挂起（至多一个），CLI 与 API 双入口共用同一业务层、SSE 逐事件可回溯；提示词全量外置、与节点解耦，保长上下文 KV cache 命中。

## 四、骨架说明与后续修改规则

### 每条遵循的骨架

> **【问题域标题】针对〔具体业务问题〕，引入〔技术方案〕，通过〔关键设计〕，实现〔可验证结果〕。**

范本（海量数据商用短链平台）的写法：「针对短链访问场景与运营管理场景存在不同查询维度的问题，设计冗余双写方案，通过 RabbitMQ 异步同步数据，构建适配不同业务场景的数据模型，降低分库分表后的查询复杂度。」

对照：

| | 范本 | 原稿的问题 |
|---|---|---|
| 开头 | 「针对…问题」先说问题 | 直接说技术，看不出为什么需要它 |
| 领域词 | 短链码、流量包扣减、支付回调验签 | 研报、公告、估值——一个都没有 |
| 标题 | 名词化问题域（分布式一致性、多维查询优化） | 技术名（「智能体协作契约」）——像报菜名 |

### 修改时的三条硬约束

1. **每条宽度 ≤ 205 显示单位**（中文按 2、英文按 1 计；A4 一行约 100 单位）。超了就是三行，会破坏整页密度。测量脚本见本节末。
2. **每条必须能读出「问题 → 方案 → 结果」**，缺问题就退回成技术堆叠。
3. **改数字必须同时给基线**（如「对比单一扁平化策略」「十次复测」），否则数字越大越像编的。

```powershell
# 校验宽度：每行一条要点
$s = @'
<粘贴要点，每条一行>
'@
foreach ($line in ($s -split "`n")) {
  $w = 0; foreach ($ch in $line.ToCharArray()) { $w += if ([int]$ch -gt 255) { 2 } else { 1 } }
  "{0,4}  {1}" -f $w, $(if ($w -le 205) { "OK" } else { "偏长" })
}
```

## 五、场景设计：三源异构为什么天然成立

| 子智能体 | 覆盖的证据链 | 为什么必须独立上下文 |
|---|---|---|
| **retriever** | 自建研报、财报、行业笔记库（docling 解析长 PDF） | 研报动辄几十页，塞进主上下文立刻膨胀 |
| **research** | 最新公告、政策、行业新闻、可比公司动态 | 搜—评—再搜要往返十几轮，全程污染主上下文 |
| **executor** | 沙箱内跑 DCF 估值、敏感性分析、因子回测、财务指标 | 必须真跑代码，且算完只该回传结论而非中间过程 |

**判据**：三类信息的**更新频率、存储位置、获取方式完全不同**——研报是静态私有资料（入库检索）、公告是每日增量（联网调研）、估值是对数据的计算（跑代码）。少任何一条结论都会失真；而三者互相独立、可并行、耗时都在分钟级，正是 `Send` fan-out 的适用场景。

### 记忆与 HITL 的落点（场景原生，非硬凑）

- **长期记忆**：关注池、持仓、风险偏好、**上次用的估值假设**（折现率、永续增长率）。次日追问同一标的直接带回上次假设——**第二次使用明显快于第一次**，这是记忆价值唯一诚实的证明方式。
- **HITL**：写入长期记忆前 `interrupt()` 确认；executor 执行有副作用的操作前确认。
- **冲突处理**：库内研报目标价与沙箱实跑 DCF 不一致时，由 answer 节点明示冲突并说明采信理由——投研场景的真实需求，也是绝佳演示点。

## 六、端到端演示剧本

**准备（离线做）**：3–5 份公开研报 PDF 上传进知识库；沙箱内预置一份静态行情 CSV。

1. **提问**：「结合我库里的研报，评估一下这份季报里 XX 公司的估值合不合理」
2. **派发**：supervisor 结构化路由 → 3 个契约并行派发（retriever 查库内研报 / research 查公告与可比公司倍数 / executor 沙箱跑 DCF + 敏感性分析）
3. **验证不阻塞**：派发后**立刻**追问「顺便看下它最近的股东减持公告」→ 主智能体正常回答 ✅ 「派发不阻塞对话」的现场证明
4. **自动汇总**：三子智能体完成后主智能体**主动**推送汇总（无需再问）：一页纸结论 + 每条标注来源 + **冲突处说明采信理由**
5. **记忆确认**：「把这次的估值假设存下来」→ `interrupt()` 确认 → 写入 PostgresStore
6. **记忆生效**：次日问「上次算 XX 用的什么假设」→ 工具直接带回，无需重算

全程 SSE 逐事件可见：路由决策 → 派发 → 子智能体进度 → 汇总。

## 八、高频追问速答

### ① 混合检索与 RAGAS 数字

**追问「0.69 → 0.90 是跟什么比？」**——对比**换内核前的旧实现**：同一份语料（500 段）、同一套 40 题、同一个最简生成器与同一个 judge，旧系统只经中间产物 jsonl 参与评估，不 import 新包。报告留档在 `eval_reports/eval_tools_rag_v1_20260922-203552.md`（末尾自动生成两个系统的并排表）。

**追问「四项指标都提升了吗？」**——口径要诚实：四项**方向全为正**（精度 0.6896→0.8958、召回 0.9000→0.9500、忠实度 0.8681→0.9595、相关度 0.4774→0.5015），但**只有上下文精度这一项明确超出判分噪声带**（实测固定输入重跑时 judge 自身抖动 Δ0.09~0.20），其余三项落在噪声内。所以对外只说「精度提升约 30%」，其余说「方向为正」。

**追问「为什么父子分块？」**——子块用于精确命中检索、父块提供完整上下文喂模型；扁平切片会把结论与依据切散，导致召回对了但模型看不懂。

### ② 「智能体通信」被问怎么答

| 方向 | 载体 | 内容 |
|---|---|---|
| 下行（主图 → 子图） | `TaskContract` 四件套，随 `Send` 发出 | `task` / `user_utterance`（用户原话，防重构失真）/ `input_data` / `output_schema_hint` |
| 上行（子图 → 主图） | `ResultSummary` 定长摘要 | `status`（success / partial / need_clarification / failed）/ `conclusion`（≤100 字）/ `key_points` / `sources` / `needs_clarification` / `warnings` |

另有两条**不在主从链路上**的契约：`Route`（supervisor 的 LLM 输出形状）、`SubgraphContract`（子图入口边界校验）。

**追问「为什么子图读不到主图 messages？」** 刻意隔离：三个子智能体各自跑长链条工具调用，若把主对话历史全给它们，token 与噪声随子图数量线性膨胀；只给四件套，子图上下文可预测、可并行、可独立替换。

**追问「子图缺信息会直接问你吗？」** 不会。子图**绝不自己 `interrupt()`**——并行时会出现多个挂起点，违反「至多一个挂起」。缺信息时填 `needs_clarification`、`status` 标为 `need_clarification`，由主智能体决定是否问用户，**挂起点只留主图一处**。

**追问「并行结果合并会不会互相覆盖？」** `subagent_results` 用 `operator.add` reducer，各分支独立 append；全批完成后由 answer 消费并清空，避免下一轮重复注入。

**追问「为什么摘要要定长？」** 让 supervisor / answer **按字段决策而不是解析长文本**。`conclusion` 卡 `max_length=100` 是故意的；反过来 `task` 字段**故意不设上限**——任务描述由 LLM 生成、长度不可控，设上限会让超长任务在子图边界直接 `ValidationError`，**崩掉整轮**。这条「该卡的卡、该放开的放开」最能体现设计判断。

### ③ 「防失控与失败摘要兜底」被问怎么答

**双层防失控**（`react.py` 注释原话：子图自数 iteration 超限优雅收尾，主图 `recursion_limit` 仅作全局兜底）：

| 层 | 机制 | 管什么 | 触发时行为 |
|---|---|---|---|
| 第一层（主动） | 子图自数 `iteration`，每轮工具 +1 | 子图内 `agent ↔ tools` 循环 | 条件边判 `iteration < max_iterations`，超限不再进 tools，转 finalize 优雅收尾 |
| 第二层（硬兜底） | 主图 `recursion_limit` | supervisor ↔ dispatch 的主图级循环 | 抛 `GraphRecursionError`，捕获后回「本轮任务循环过深，已中止」并打 `taskforce_error` 标记 |

**上限是分级的**：`retriever 5` / `research 8` / `executor 12`——检索一两轮够，代码执行要多轮试错。另有 `WRAPUP_HINT` 在接近上限时注入，让模型先自己收尾（软提醒与硬闸门互补）。`answer` 侧还有独立防线 `MEMORY_LOOP_MAX = 4` 管记忆工具循环。

**失败摘要兜底**（`tasks.py._run`，注释：「异常兜底为 failed 摘要，绝不炸线程」）——三种失败都收敛成结构化摘要：

| 场景 | status |
|---|---|
| 被轮数上限截停 | `partial`（conclusion：「检索轮数达上限，返回当前所得」+ warnings） |
| 无命中/缺信息 | `need_clarification`（填 `needs_clarification` 交回主图） |
| 真抛异常 | `failed`（`conclusion` 截断至 100 字 + warnings） |

价值：主智能体**永远拿得到一份契约合规的摘要**，「某个子智能体挂了」只是汇总里的一条坏消息，不是整轮失败。

> **最值得主动讲的坑**：`ResultSummary.agent` 是 `Literal[...]`，若 agent 名为未知值，**在 except 里构造摘要会再次 `ValidationError` 并被线程静默吞掉**——任务永不返回、整批永远等不齐。故兜底路径先 `safe_agent = agent if agent in _BUILDERS else "retriever"` 归一、再截断结论。**「兜底代码自己也会失败」这个认知很显功夫。**

### ④ 「AI 辅助开发怎么保证代码是对的？」

答三件真实机制：契约在子图之前先定稿，接口不会边写边变；模块按编号推进、依赖未完成不开工；测试与业务代码分开负责，后端 236 个测试覆盖路由、契约、任务回收。**不要答「我会 review AI 的代码」**——那句话不构成机制。
